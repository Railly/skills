# Solution gate: synchronized-output deadline ownership (PR #106)

Date: 2026-08-08. Target defect head `e245e37`; implementation head `01b7809`.
Proposers: `anthropic/claude-opus-5` and `google/gemini-3.1-pro-preview`, both through Vercel AI Gateway against isolated detached worktrees at `e245e37`.
Synthesis and implementation: Codex GPT-5 family.

## Trigger

Fires because this is a fix for an external review finding and changes the contract between the core generation signal and the DOM render scheduler. S1 and S2 receive extra weight.

## Neutral defect contract

**Property violated.** While synchronized output is held, a distinct core generation does not receive an independent bounded hold; the DOM scheduler can apply a prior generation's deadline to the new block. At `packages/@wterm/dom/src/wterm.ts:226-255` on `e245e37`, the DOM observes a changed generation but only updates its stored number instead of establishing a new deadline.

**Observable that must change.** With the real committed WASM, send `BSU+A`, wait 600 ms, then one write containing `ESU+BSU+B`. Generation 2 must remain unpainted for 999 ms after its BSU and recover at about 1000 ms after generation 2 began. Separately, `BSU+A`, wait 900 ms, ordinary payload `B` must still recover at about 1000 ms from the original BSU.

**Must not change.**

- ESU paints early.
- An unterminated block recovers.
- Ordinary payload cannot postpone recovery indefinitely.
- A later BSU after recovery starts a fresh atomic hold.
- Queued-render and destroy cancellation remain correct.
- Callback failures still drain parser responses and schedule recovery/render before rethrow.
- The optional `TerminalCore` capability remains source-compatible.

## Proposal A: Claude Opus 5, verbatim

### Shape

**One record, one owner.** Replace the DOM's two loosely-coupled fields (a stored generation number and a separately-armed deadline/timer) with a single nullable hold record owned exclusively by the DOM scheduler:

- `hold: { generation: number; deadlineAt: number } | null` — the *only* place a synchronized-output deadline exists. Generation and deadline are written together or not at all; there is no code path that assigns one without the other.
- `releasedGeneration: number` — the highest generation whose hold was already force-released by timeout, so a released block cannot re-arm itself on subsequent writes.
- One timer handle, armed only from `hold.deadlineAt`.

**Who owns what.** The core (WASM) owns *identity and liveness*: after a write is fed to the parser, it reports `{ active, generation }` — generation monotonically increments on each BSU, including a BSU that immediately follows an ESU inside the same write. The DOM owns *policy and time*: the 1000 ms bound, the clock, the timer, and the decision to paint. No wall-clock or deadline value crosses the boundary, so `TerminalCore`'s optional capability keeps its exact current signature and this is a DOM-local change.

**The transition rule**, evaluated once per write in the existing post-parse drain block (the same block at wterm.ts:226-255, so the ordering guarantee "drain parser responses → schedule recovery/render → rethrow on callback failure" is untouched):

1. `active === false` → `hold = null`, cancel timer, render now. (ESU paints early; unchanged.)
2. `active === true` and `hold?.generation === g` → do nothing. The existing `deadlineAt` survives. (Ordinary payload cannot extend the hold; the 900 ms case still fires at 1000 ms from the original BSU.)
3. `active === true` and `g <= releasedGeneration` → do nothing, stay painted. (An already-recovered unterminated block does not re-hold on later writes.)
4. Otherwise (`g` is new) → `hold = { generation: g, deadlineAt: now() + 1000 }`, cancel-and-rearm the timer. This is the fix: a changed generation *establishes a new deadline* rather than mutating a number.

**Timer fire:** if `now() < hold.deadlineAt` (clamping/drift), re-arm to the remainder; otherwise set `releasedGeneration = hold.generation`, `hold = null`, render. **Destroy:** single cancel point clears the timer and nulls `hold`, and must run after any queued render is cancelled — unchanged from today.

**Public contract:** unchanged. `TerminalCore`'s sync capability stays optional and same-shaped; a core that omits it means `hold` is permanently `null` and every write renders as before. The DOM adds no new public surface.

### Predictions

1. **New regression test, fake timers.** Write `BSU + "A"`; advance 600 ms; single write `ESU + BSU + "B"`. Measure the render/paint callback invocation count: it is 0 at +999 ms after that second write and exactly 1 at +1000 ms (±1 tick). Under HEAD the same measurement yields 1 at +400 ms. Command: the package's test task, e.g. `pnpm --filter @wterm/dom test` filtered to the synchronized-output suite.
2. **Existing behaviour pinned.** Write `BSU + "A"`; advance 900 ms; write plain `"B"`. Paint count is 0 at 999 ms and 1 at 1000 ms measured from the *original* BSU (i.e. 100 ms after the `"B"` write), never 1900 ms. Additionally, spy on `setTimeout`/`clearTimeout` in that scenario: exactly one sync-recovery timer is armed and never re-armed, because rule 2 short-circuits.
3. **Precondition check on the real WASM (falsifies the whole shape if it fails).** Feed `ESU + BSU` as one write to the committed core and read the reported generation: it must be `2` with `active === true`. If the core instead reports generation `1` (increment only on inactive→active), the DOM cannot distinguish the new block and this shape is wrong — the fix then has to move into the core. The contract's own wording ("the DOM observes a changed generation") predicts `2`.
4. **No lone generation writes.** `git grep -n "generation" packages/@wterm/dom/src/wterm.ts` shows every assignment occurring as part of constructing the `hold` record; there is no surviving statement that updates a generation field alone. This is the structural invariant that makes the class of defect unrepresentable.
5. **Unchanged invariants.** Throwing from the write callback still leaves parser responses drained and a recovery timer armed for the current generation before the rethrow (assert via spy ordering); `destroy()` during an active hold leaves zero pending timers (assert timer-spy balance).

### Cost

Small and local: one struct field replacing two, one added `releasedGeneration` counter, roughly 25–40 lines of the DOM write path rewritten, no core/WASM rebuild, no interface change, no migration. Two new tests plus one precondition assertion on the real core. Runtime cost is one extra `clearTimeout`/`setTimeout` pair per *generation change* (not per write), which is strictly cheaper than the naive re-arm-every-write alternative. Review cost is low because the change is confined to one function and one destroy path. The main non-code cost is verifying prediction 3 against the committed WASM before committing to a DOM-only fix.

### What it makes worse

- **Adversarial starvation becomes reachable.** A stream that emits `ESU + BSU` repeatedly now gets a fresh 1000 ms hold each time, so painting can be postponed indefinitely. Previously the stale deadline acted as an accidental global cap. This is implied by "a later BSU starts a fresh atomic hold", but it is a real worst-case-latency regression and there is no total cap in this shape. If a cap is wanted later it has to be a separate, explicitly-specified budget.
- **Hidden monotonic assumption.** `releasedGeneration` assumes generations never go backwards. A full terminal reset (`RIS`) or core re-init that restarts the counter would make a legitimate new block look already-released and it would never hold. Mitigation is a one-line "if `g < releasedGeneration`, treat the counter as reset" clause, but that is extra state semantics the current code does not have, and it is only correct if the core really does reset the counter — an untested edge today.
- **Clock coupling.** The hold now stores an absolute `deadlineAt` from the DOM's clock. Under suspended/backgrounded tabs or coarse timer clamping the recovery lands late; the re-arm-on-early-fire loop mitigates but does not eliminate this, and it makes the timing assertions in the tests tick-sensitive.
- **One more state that destroy must clear**, i.e. a new way to leak a timer if a future code path returns early from the drain block.

### Rejected alternatives

- **Re-arm the deadline on every write while active.** Simplest possible change, but directly violates the 900 ms/ordinary-payload observable: `"B"` would push recovery to 1900 ms and let non-BSU output postpone painting forever.
- **Re-arm only on an observed inactive→active transition.** Fails the headline case: `ESU + BSU` in one write never produces an observed inactive state, so generation 2 would inherit generation 1's deadline — the exact defect.
- **Move the deadline into the core / have the core return remaining-milliseconds or an absolute expiry.** Puts wall-clock policy in the WASM, requires a core rebuild, breaks source-compatibility of the optional capability, and makes the DOM's injected clock and fake timers useless for testing. Timing policy belongs on the side that owns the paint.
- **Re-scan the write buffer in the DOM for BSU/ESU byte sequences.** Duplicates the parser, and breaks the moment an escape sequence is split across two writes or arrives inside a payload that the parser would have treated differently.
- **A `Map<generation, deadline>` of per-generation holds.** Unbounded growth, needs eviction, and buys nothing: only the newest un-released generation can ever be the active hold, so a single record is complete.
- **Paint at the ESU before honouring the following BSU.** Would require the core to surface intra-write events rather than post-write state, i.e. a core change and a new public contract, and it contradicts the stated observable that generation 2 stays unpainted.

## Proposal B: Gemini 3.1 Pro Preview, verbatim

### Shape

State lives in the DOM scheduler (within `wterm.ts`), which tracks the last observed `syncGeneration` (an integer) and the active `recoveryTimeout` (a timer handle). The DOM scheduler exclusively owns the deadline and the timer. The public contract remains a polling/observational model: the Core exposes its current synchronization generation, and the DOM scheduler reads it during its update cycle. When the DOM scheduler processes a batch and observes that the Core is in a synchronized hold, it compares the Core's generation to its tracked `syncGeneration`. If the Core's generation is strictly different (greater), the DOM scheduler clears any existing `recoveryTimeout`, establishes a new independent bounded hold (e.g., a fresh 1000 ms timeout), and updates its tracked `syncGeneration`. If the generation is unchanged, the existing timeout is left to run.

### Predictions

1. If a script writes `BSU + "A"`, pauses for 600 ms, and then writes `ESU + BSU + "B"`, the terminal will not paint "B" until approximately 1600 ms after the initial write (exactly 1000 ms after the second BSU established the new generation).
2. If a script writes `BSU + "A"`, pauses for 900 ms, and then writes an ordinary payload `"B"` (without an intervening ESU or BSU), the terminal will forcefully recover and paint both "A" and "B" at approximately 1000 ms from the initial BSU, proving that ordinary payloads do not reset the deadline.

### Cost

The runtime cost is O(1) per processed batch, requiring only an integer comparison and, strictly on generation boundaries, a `clearTimeout` and `setTimeout` call. The memory cost is zero additional allocations, as it reuses the existing timer handle and generation tracking fields.

### What it makes worse

A misbehaving or malicious application can now indefinitely starve the terminal's render pipeline by repeatedly sending `ESU + BSU` just before the 1000 ms deadline expires. While ordinary payloads cannot postpone recovery, explicitly chaining new generations forces the DOM to continuously defer painting, potentially leading to a frozen UI until the stream ends or the application stops issuing BSUs.

### Rejected alternatives

- *Moving deadline ownership to the Core:* The WASM core could track the timeout and emit a recovery signal. Rejected because it violates the constraint to keep the optional `TerminalCore` capability source-compatible, and timer management is inherently an environment-specific (DOM) responsibility.
- *Resetting the deadline on every write while synchronized:* The DOM could simply clear and reset the timeout whenever new bytes arrive during a hold. Rejected because it violates the defect contract: ordinary payloads must not postpone recovery indefinitely.
- *Maintaining a queue of deadlines:* The DOM could track a separate timeout for every generation seen in a single batch. Rejected because only the most recent generation's deadline is relevant for the active hold; older generations in the same batch are already implicitly terminated by the newer BSU.

## Synthesis

**Kind: one proposal whole in contract, narrower graft in implementation.**

Take Gemini's minimal shape and the shared ownership conclusion from both proposers:

- The DOM renderer owns the watchdog.
- Every observed generation change while held cancels the prior timer and arms a fresh 1000 ms timer.
- An unchanged generation leaves the timer untouched, so ordinary payload does not extend the deadline.
- The timeout callback is bound to the captured generation so a stale callback cannot release a newer block.
- Public prose says “at most one second from the opening sequence,” not “one second of inactivity.”

Do not take Opus's `releasedGeneration`, absolute `deadlineAt`, or reset-counter policy. The existing `idle | held | passthrough` model already prevents a timed-out generation from re-holding and recognizes a later generation. Adding parallel state would repeat S1 and create reset semantics outside Tate's finding.

Gemini's genuine downside remains: an application can explicitly chain fresh synchronized generations forever. This is accepted because each BSU declares a new atomic block; imposing a global ceiling across distinct blocks would be a separate public contract.

## Carried assumptions

- Core generation increments for `ESU → BSU` within one write. Verified with committed WASM.
- Generation is observed after parsing and response draining. Verified by the combined #105/#106 write path.
- A stale timeout callback cannot affect a newer generation. Verified by captured-generation comparison.
- Browser timer clamping may make recovery later than 1000 ms in background tabs. Accepted existing platform behavior; no stricter wall-clock promise is documented.

## Must-not-change handoff to Review Gate

- ESU paints early.
- Ordinary payload never re-arms the synchronized-output timer.
- Every distinct generation gets a full deadline.
- Timeout recovery paints and permits a later BSU to hold again.
- Queued RAF and destroy cancellation stay force-red covered.
- Callback failures preserve the first thrown value while completing response drain and render/recovery bookkeeping.
- Committed WASM matches the combined Zig sources from #105 and #106.
