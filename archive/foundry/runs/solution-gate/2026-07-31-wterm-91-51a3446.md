# Solution gate: vercel-labs/wterm#91 — scrollback readback

Date: 2026-07-31. Target commit: `51a3446` (wterm main, after #96).
Runtimes — proposers: `fable-5` (A) and `gpt-5.6-sol` @ high effort (B). Synthesis/implementation: `claude-opus-5`.
Isolation: both proposers in separate clones under `~/Programming/vercel/_sg91/{p1,p2}`. No candidate shape existed, so nothing needed sealing.

## Step 0 — Trigger

Fires. Two clauses: the defect admits more than one shape (where the page walk is cached, what the return value means), and the change alters a contract between the WASM boundary and the DOM renderer.

## Step 1 — Defect as contract

**Property violated.** The ghostty core publishes a scrollback contract it does not honor: `get_scrollback_count` reports N retained rows, and every accessor for the content of those rows returns "empty" rather than either the content or an error.

**Observable that must change.** `getScrollbackLineLen(offset)` returns the row width and `getScrollbackCell` real codepoints, verified against `@wterm/core`'s `WasmBridge` on an identical write sequence.

**Must not change.** `get_viewport` output including the #96 style_id gating and #93 color_flags semantics; `get_scrollback_count` values; the 16-byte cell layout; alt-screen isolation; resize safety; no new per-cell allocation.

## Step 2 — Proposals

Both agreed on ownership (libghostty's page list stays the sole store, no mirrored history) and on offset 0 = the row immediately above the viewport. Their agreement carried no weight until step 3 probed it.

They diverged on three things:

| | A (fable-5) | B (gpt-5.6-sol) |
|---|---|---|
| Return value | `1 + last non-empty index` (trimmed), claiming it mirrors the built-in core | stored grid width, claiming it mirrors `WasmBridge` |
| Zig-side state | none; re-derive from `getTopLeft(.active)` + `Pin.up(offset+1)` each call | cached page-list locator from `getBottomRight(.history)`, invalidated on write/resize |
| `get_viewport` | extract shared `encodeCell` helper, used by both paths | leave untouched, duplicate the packing |

Both proposed the same TS amortization: one persistent `cols * CELL_BYTES` buffer plus a per-row cache so the renderer's per-column access costs one WASM call per row instead of one per cell.

A alone named two things B missed: multi-codepoint graphemes degrade to the base codepoint when reading pages raw, and old-wasm/new-TS silently returns 0-length lines.

## Step 3 — Probe log

Environment: fresh clone at `~/Programming/vercel/wterm`, committed wasm byte-identical to a local rebuild attempt's input (`cmp` → IDENTICAL).

**P1 — defect reproduces, offset semantics.** `bun probe1.mjs`
```
ghostty count: 77   ghostty len(0): 0   ghostty len(76): 0
core count: 77      core len(0): 80
core offset0 text: "line-77"
core offset76 text: "line-1"
```
→ Defect confirmed. **Offset 0 = newest retained row** (SURVIVES for both A and B).
→ **`WasmBridge` length is 80, the grid width, not the 7-char trimmed text.** This **refutes A's stated justification** ("mirrors the built-in core's stored `len`") and confirms B's contract.

**P2 — length contract, alt screen, resize.** `bun probe2.mjs`
```
core lens sample: [80, 80, 80, 0, 0]      # always cols for populated rows, 0 out of range
ghostty count primary: 77
ghostty count on ALT: 0
ghostty count back to primary: 77
ghostty count after resize 40x12: 89
ghostty count after resize back: 77
```
→ Length is invariably `cols`. A's trimmed contract is a divergence, not a mirror.
→ Alt-screen isolation already holds by reading `screens.active`; both proposals' alt predictions SURVIVE structurally.
→ Resize reflow is non-destructive. Both resize claims SURVIVE.

**P3 — is the artifact buildable?** This is the probe neither proposal thought to specify, and both of their primary predictions are phrased as "after `pnpm --filter @wterm/ghostty rebuild-wasm`, vitest shows X".
```
$ pnpm --filter @wterm/ghostty rebuild-wasm
Using Zig: ~/.local/share/zigup/0.15.2/files/zig (0.15.2)
error: undefined symbol: __availability_version_check
error: undefined symbol: _abort / _arc4random_buf / _bzero / _clock_gettime / _dispatch_* ...
Exit status 2
```
Reproduced with a pristine `zig-aarch64-macos-0.15.2` downloaded from ziglang.org — not a local install problem. Host is macOS 26.5.2; Zig 0.15.x cannot link a host build runner against this libSystem.

The other direction also fails:
```
$ zig build -Doptimize=ReleaseSmall     # zig 0.16.0
ghostty-1.3.1/pkg/breakpad/build.zig:15:8: error: no field or member function named 'linkLibCpp'
```
→ **The ghostty wasm cannot be built on this machine with either toolchain.** `build-wasm.sh` pins Zig 0.15.x (ghostty 1.3.1's requirement); 0.15.x is dead on macOS 26; 0.16 breaks inside ghostty's vendored build files.

Compounding: `.github/workflows/ci.yml` builds and diff-checks only `@wterm/core`'s wasm. It never builds `@wterm/ghostty`'s. The committed `ghostty-vt.wasm` is a hand-produced binary with no CI verification that it matches `wasm_api.zig`.

→ **Both proposals' primary predictions are UNPROBEABLE in this environment.** Recorded as unverified assumptions, not upgraded to facts.

## Step 4 — Shape scoring

| Shape | A | B |
|---|---|---|
| **S1 over-reach** | **HIT.** Refactors `get_viewport`'s per-cell encode into a shared helper. | **S2 under-reach** | **HIT.** Closes "text is blank" but ships a length the reference implementation does not use. `renderer.ts:364` passes `lineLen` as the cell-count bound, so a ghostty scrollback row would build 7 cell elements where the built-in core builds 80. | clean — contract matched to the probed reference |
| **S4 proxy property** | **HIT.** Its parity test asserts *text* equality, which both length contracts satisfy. The guard cannot see the divergence the guard exists to catch. | clean |
| **S5 unregistered peer** | mild — TS cache keyed to the existing `_invalidate()`; A named the staleness risk itself | **HIT (named).** Adds Zig-side locator state every future mutating export must invalidate. |
| **S6 peer-version blindness** | partial hit, **named** — "old wasm + new TS returns 0-length lines silently" | **HIT, unnamed.** |
| **S9 test pins wrong thing** | **HIT** — see S4; the parity test passes whether or not the length contract is right | clean — its call-count spy fails if the amortization mechanism is deleted |
| **S10 claim from prose** | **HIT, refuted by P1** — "mirrors the built-in core's stored `len`" was read, not run | clean on the length claim; **both hit** on citing a build command neither executed |

## Step 5 — Synthesis: graft

**Take B's contract and A's stateless read.**

- **From B:** return value = stored grid width (`min(row_width, max_cols)`), offset 0 = newest, signature unchanged, `get_viewport` untouched with the cell packing duplicated. Probe-backed on every point.
- **From A:** the stateless Zig read — re-derive the row from the active screen's page list on each call, no cached locator. This drops B's only S5 hit. B's locator optimizes sequential locality that no measurement demanded, and the walk is bottom-up so the offsets the renderer actually requests (small, near the viewport) are already the cheap ones.
- **From A, as knowledge not mechanism:** the grapheme limitation and the wasm/TS version-lock go in the record and the PR description. B never surfaced either.
- **Rejected from A:** the trimmed length (refuted by P1), the `get_viewport` refactor (S1), and the text-only parity test (S4/S9). The test must assert length as well as text.
- **Rejected from B:** the Zig locator (S5), for the reason above.

**Seam check.** A's walk (`getTopLeft(.active)` then `Pin.up(offset+1)`) and B's (`getBottomRight(.history)`) must resolve to the same row for offset 0. Composed shapes can satisfy both proposers' predictions and violate a property neither watched — this equivalence is not proven and is carried below.

## Carried assumptions (verify during implementation, not before)

1. `getTopLeft(.active).up(offset+1)` and `getBottomRight(.history).up(offset)` name the same row for every valid offset. Neither probe touched this.
2. `min(row_width, max_cols)` reproduces `WasmBridge`'s 80 for every populated row, including rows shorter than the grid and rows after a reflowing resize. P2 sampled five offsets on one geometry.
3. Reading `node.data.styles.get(...)` gated on `style_id != 0` reproduces the #96 semantics for history rows. Untested — #96 was verified against `RenderState`, not against raw page reads.
4. Both proposals' vitest predictions. **Unprobeable here** until the toolchain question is answered.

## Must-not-change list → Review Gate step 5

Each entry gets driven, not reasoned about:
- `get_viewport` byte output for a fixed input sequence, before vs after.
- `get_scrollback_count` values across the P2 sequence (77 / 0 on alt / 77 / 89 after resize / 77).
- Alt-screen: no primary scrollback readable while alt is active.
- Resize with populated scrollback: no trap, no leak, history still readable.
- The 16-byte layout: `parseCell` and the dom renderer both bake in 16.

## Issue candidates found by probing, outside this scope

1. **`@wterm/ghostty`'s wasm is unbuildable on macOS 26** — `build-wasm.sh` requires Zig 0.15.x, which cannot link a host build runner against macOS 26's libSystem; Zig 0.16 fails inside ghostty 1.3.1's vendored `pkg/breakpad/build.zig`. Any contributor on a current macOS is blocked from touching `wasm_api.zig` at all. This is a precondition for #91, not a side note.
2. **CI does not verify the committed `ghostty-vt.wasm` against its Zig sources**, while it does exactly that for `@wterm/core`. The binary can silently drift from `wasm_api.zig`.

## Correction to P3, after Hunter asked whether the committed wasm is trustworthy

Three findings revise the P3 write-up above. Left in place rather than edited, since the
first version is what the synthesis was made against.

**1. The committed wasm is NOT orphaned. Proven behaviorally.**
`git show a523f76:...ghostty-vt.wasm` (pre-#96) differs from HEAD's (428644 vs 428683 bytes).
Swapping the old binary in and running the suite:
```
wasm pre-#96 : Test Files 1 failed | 1 passed ; Tests 3 failed | 2 passed
wasm at HEAD : Test Files 2 passed         ; Tests 5 passed
```
The style-leak tests fail against the old binary and pass against the committed one, so the
committed artifact does contain #96's Zig change. The drift worry is unfounded for the most
recent change. What remains true is that nothing *automated* establishes this — the check
above was run by hand.

**2. The zigup install was symlinks into `/tmp`.**
`~/.local/share/zigup/0.15.2/files/{zig,lib}` were symlinks to `/tmp/zig-aarch64-macos-0.15.2`,
created 2026-07-28 00:18 — the same session as the #96 rebuild. macOS reaps `/tmp`. Reinstalled
under `~/.local/share/zig/` and repointed. This did not fix the build, but it means the
toolchain was one `/tmp` sweep from vanishing regardless.

**3. Sharper mechanism than "0.15.x is dead on macOS 26".**
Zig 0.15.2 links a native binary fine when the target is pinned:
```
$ zig build-exe t.zig -target aarch64-macos.15.0.0 -femit-bin=a4
$ ls -la a4    ->  1198640 bytes, real binary
```
and fails on the auto-detected `aarch64-macos.26.5.2` (host is macOS 26.5.2, installed
2026-07-06, so the OS did not change between the working build and this one). It is a
target-detection/libSystem-tbd problem, not a hard impossibility.

Workarounds that do NOT work, each verified: `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX15.sdk`,
`DEVELOPER_DIR=/Library/Developer/CommandLineTools`, `--sysroot`, `-lc`, and `zig build --host-triple
aarch64-macos.15.0.0` (0.15.2 has `--host-triple`, not `--host-target`; it did not change the
runner's link). Two of these initially read as successes and were not: zig emitted a **0-byte**
output file while erroring, so an `ls` check passed. Only the `-target` run produced a real binary.

**Not root-caused:** why the build succeeded on 2026-07-28 and fails on 2026-07-31 with the same
OS, same Zig version, and cleared caches. Recorded as unexplained rather than guessed at.

**Consequence for the shape.** Unchanged — the graft in step 5 stands. What changes is sequencing:
the only host-native artifact in this build is the build runner, and `zig build` in 0.15.2 offers
no way to pin its target. Either the runner problem is solved, or the wasm is produced somewhere
that is not this machine.

**Revised issue candidates.**
1. `build-wasm.sh` depends on a Zig that cannot link a host build runner on macOS 26. Pinning the
   target fixes direct compiles but there is no exposed knob for the build runner in 0.15.2.
2. CI builds and diff-checks `@wterm/core`'s wasm and never touches `@wterm/ghostty`'s. The
   hand-run check in finding 1 is exactly what the workflow should do, and it would run on Linux
   where this toolchain is not affected.

## P4 — the build question, resolved

Hunter asked to investigate the "bypass the build runner" option. It is dead, and probing it
surfaced a better answer.

**Why the bypass fails.** The wasm target is not the problem. `ghostty-vt` needs `unicode_tables`
and `symbols_tables`, generated by running two **host-native** executables (`props-unigen`,
`symbols-unigen`, built for `b.graph.host` in `src/build/UnicodeTables.zig`). Those consume a
`tables.zig` that uucode generates by running *its own* host executable. Three chained levels of
host codegen, and host-native linking is exactly what is broken. Hand-rolling around the build
runner means reimplementing ghostty's build graph, not skipping a step.

Also ruled out along the way: no Zig 0.15.3+ exists (0.15.2 is the last 0.15.x), and
`MACOSX_DEPLOYMENT_TARGET=15.0` does not change native link behavior (0-byte output, exit 1).

**What works: a Linux container.**
```
docker run --rm -v <repo>:/work -v <script>:/build.sh alpine:3.20 sh /build.sh
  # apk add curl xz bash python3; fetch zig-aarch64-linux-0.15.2; bash scripts/build-wasm.sh
->  Built: /work/packages/@wterm/ghostty/wasm/ghostty-vt.wasm   418.6K
```
Unmodified sources, unmodified `build-wasm.sh`. python3 is required by `patch-ghostty-wasm.sh`
and is the only non-obvious package.

**The build is reproducible across platforms.** The container output is **byte-identical** to the
committed artifact:
```
$ cmp /tmp/committed.wasm packages/@wterm/ghostty/wasm/ghostty-vt.wasm
BYTE-IDENTICAL   (428683 bytes)
$ pnpm --filter @wterm/ghostty test    ->  5 passed
```

This upgrades the finding from the previous section. The behavioral check proved the committed
wasm contains #96's change; this proves bit-for-bit that it is exactly what `wasm_api.zig` at
`51a3446` compiles to. The drift question is fully answered, and it is answered by a command
anyone can run.

**Consequences.**
- #91 is unblocked with a working local loop; no CI round-trip needed to iterate on Zig.
- The CI diff-check for `@wterm/ghostty` is now known-meaningful rather than hoped-meaningful:
  reproducibility across host platforms is demonstrated, so a Linux CI job can legitimately
  diff its output against the committed binary, exactly as the existing `@wterm/core` job does.
- The macOS host-link failure stops being a blocker and becomes a papercut: worth a note in
  `build-wasm.sh` pointing at the container path when the host toolchain refuses.

## Outcome

Shape decided. The gate surfaced a blocker that would have been discovered after writing the Zig, and then dissolved it: the build is reproducible in a Linux container, byte-identical to the committed artifact. Second recorded use of this skill; still zero evaluations.
