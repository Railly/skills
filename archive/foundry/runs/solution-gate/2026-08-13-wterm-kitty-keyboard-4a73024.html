wterm Kitty keyboard protocol

Solution Gate on 4a73024, August 13, 2026.

Observed behavior

Current built-in core

observed CSI ? u produces no reply. Push is unhandled. Set and pop cannot establish Kitty state.

Plain CSI u is already cursor restore and must remain so.

Current Ghostty wrapper

observed Native Ghostty parses and mutates Kitty state, but the readonly wrapper drops the query.

The observable defect is missing export and response, not missing native state.

Real Ghostty state

observed Temporary real-WASM export measured 0 → 5 → 7 → 6 for push, OR, and NOT.

Primary and alternate screens hold independent stacks. DECSTR preserves them. RIS clears them.

Exact query seam

observed A temporary Zig handler reading the active native stack returned exact replies such as CSI ?6u and alternate CSI ?9u.

No TypeScript state copy was required.

Browser substrate

observed Chromium exposes key, code, location, repeat, modifiers, composition state, keydown, and keyup.

It does not synchronously provide a reliable base-layout mapping or events that the platform never delivers.

Green baseline

observed DOM 145/145, Ghostty 49/49, and Zig tests passed before implementation.

Those legacy behaviors form the regression tripwire.

Accepted contract

  1. Each core owns an eight-entry Kitty stack per screen.
  2. The built-in core matches Ghostty push, pop, set, OR, NOT, DECSTR, RIS, and alternate-screen semantics.
  3. kittyKeyboardFlags?(): number is optional. Absence or zero means legacy behavior.
  4. Ghostty answers query inside Zig from screens.active.kitty_keyboard.
  5. One pure TypeScript module encodes Kitty events for both cores.
  6. Plain CSI u, IME, shortcuts, paste, focus, mouse, and all legacy bytes remain unchanged.
  7. Unsupported browser information is omitted and tested, never invented.
