Portless path routing

Solution Gate on isolated origin/main at 93acac4, August 13, 2026.

Observed behavior

Current name grammar

observed parseHostname("app/api") returns app.localhost.

Slash suffixes are already discarded. Reusing them as route syntax changes an existing input.

Current authority precedence

observed exact hostname → Tailscale authority → Tailscale hostname → wildcard.

A path match cannot be allowed to skip to a weaker tier.

Current state downgrade

observed An old proxy first-matches duplicate hostnames and ignores extra path fields.

observed Old add/force filters every row with that hostname, then writes one pathless row.

Current data plane

observed HTTP, upgrade, and extended CONNECT all resolve a route and forward raw req.url.

The new matcher can preserve full-path forwarding.

inferred --path/config → canonical stored prefix

Harmful branch: old proxies cannot safely serve new duplicate-hostname state. Accepted and documented.

Proposal B: positional app/api

observed slash currently discarded → inferred mixed versions assign different meanings

guessed tier with any path match → inferred exact hostname can lose to Tailscale/wildcard

guessed old CLI fails safely → observed refutation old proxy first-wins and force wipes siblings

Verdict: rejected. It breaks grammar, precedence, and downgrade behavior.

Accepted contract

  1. Identity is (hostname, canonicalPathPrefix); missing prefix is root.
  2. Authority is resolved first. Path specificity is resolved only inside the winning hostname set.
  3. No path match returns 404, never a weaker authority tier.
  4. All three request transports share the matcher and forward the original path.
  5. Add, update, force, remove, rollback, and cleanup use tuple identity.
  6. Hostname consumers use set semantics and remain active while any sibling route exists.
  7. New code reads old state. Old code serving new duplicate-host state is unsupported.
