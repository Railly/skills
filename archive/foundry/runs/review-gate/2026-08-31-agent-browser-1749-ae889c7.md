## Findings

- F1: confirmed, open. A close can lose its cancellation signal because watch::Sender::send(true) discards the value when no receiver exists; a command that subscribes after the closing checks can keep the state lock and hang close indefinitely. Evidence: Production ordering is cli/src/native/daemon.rs:491-526 and publication is line 424. Tokio 1.53.1 explicitly does not retain send values with zero receivers. Vercel Agent Review independently reported the exact race at the frozen head.
- F2: confirmed, open. PID fallback termination can kill an unrelated process because the target PID is not validated as the current advisory-lock owner before signaling. Evidence: Direct exact-head dogfood substituted a live unrelated sleep PID while the real daemon retained the owner lock. close --all killed the sleep and left the real owner alive. The same raw-PID signaling hazard exists in kill_stale_daemon.
- F3: confirmed, open. If a close client disconnects before the terminal response is written, the daemon skips close_notify and remains alive in session_closing state with socket, PID, and ownership lock intact. Evidence: Direct raw-socket dogfood observed browser cleanup but persistent daemon and sidecars. A second close replayed the terminal response and released the daemon.
- F4: confirmed, open. The full command reference omits the new session_busy, cancellation, close recovery, and MCP lifecycle contract required by the canonical surface map. Evidence: gate.sh surfaces flagged skill-data/core/references/commands.md. Lines 27 and 363-393 still advertise terse close and MCP behavior without the new outcomes or recovery guidance.
- F5: unverified, open. The recording task can fill its piped ffmpeg stderr, hit the two-second wait timeout, kill ffmpeg, and return success with a truncated recording. Evidence: cli/src/native/recording.rs:117 keeps stderr piped while lines 201-208 changed from wait_with_output to wait and the timeout branch returns Ok. No long recording or controlled full-pipe producer was executed.
- F6: unverified, open. A losing concurrent close can return session_closing after seven seconds while the winning close is still completing a valid longer cleanup path. Evidence: cli/src/native/daemon.rs:545-552 waits seven seconds. The graceful budget is five seconds and the forced provider, WebDriver, and Appium paths each contain sequential two-second waits.
