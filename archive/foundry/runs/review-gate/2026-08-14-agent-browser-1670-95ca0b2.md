## Outcome

The branch keeps `--ca-cert` as a shared trust input for two independent consumers:

- CLI-owned TLS always receives the supplied CA.
- A local Chromium launch on Linux also receives private NSS trust and requires `certutil`.

`--cdp`, `--auto-connect`, providers, and CLI-only actions use the CA only for CLI TLS. `--use-system-ca` affects only CLI TLS. Local browser-side CA trust remains rejected on macOS and Windows.

Two review findings were fixed:

1. The daemon rejected `--ca-cert` for remote attach and provider modes even though those modes still need CLI TLS trust.
2. `--ca-cert` caused CLI-only actions such as `read` to request an accidental local browser launch.

## Subsystem model

The CLI process resolves trust configuration before local commands, provider calls, CDP discovery, WebSocket connections, downloads, upgrades, and AI Gateway requests. A spawned daemon receives the same trust environment. Browser-side CA validation is separate and runs only when the daemon launches local Chromium on Linux.

`native::actions::skip_launch_action` is the single source of truth for actions that must not request browser launch configuration. Remote attach paths retain the CA for daemon-owned CLI TLS but remove it before browser launch validation.

The affected consumers are flags and config, process environment, daemon options, CDP clients and discovery, providers, reqwest clients, stream chat, doctor output, MCP, Eve, published schemas, CLI help, README, web docs, and skill docs.
