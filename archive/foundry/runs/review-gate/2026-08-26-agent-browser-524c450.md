## Outcome

The PR fixes its main bug. On a real Windows ARM64 host, the merge-base launcher fails when
only the published x64 binary exists. The head launcher selects that x64 binary and exits 0.
The same published x64 PE, confirmed as COFF `0x8664`, runs through Windows emulation and
returns `agent-browser 0.35.0`.

The PR also preserves the native path. The first-party producer built
`agent-browser-win32-arm64.exe`, 12,548,608 bytes, COFF `0xAA64`. It ran successfully, and
the launcher selected it whenever it was present.

Real Windows ARM64 resolution matrix from run `33002500967`:

| Files in `bin/` | Base `8934fdb` | Head `524c450` |

| arm64 only | arm64, exit 0 | arm64, exit 0 |
| neither | exit 1, expects arm64 | exit 1, expects x64 |

The load-bearing change is the x64 fallback. It turns the standard postinstall layout from
total launcher failure into a working CLI.

## Findings

### F2: the no-binary error names two architectures

Confirmed on real Windows ARM64. In the head's neither-present cell, the launcher exits 1
with `No binary found for win32-arm64`, then says it expected
`agent-browser-win32-x64.exe`. Base named arm64 on both lines, so the inconsistency is new in
this diff.

Fix by naming the resolved fallback explicitly or using one architecture model on both
lines.

### F3: the committed suite leaves three protection gaps

The PR suite covers x64-only, both, arm64-only, and Darwin. It does not cover the
neither-present failure path that exposes F2. It does not exercise the npm-generated global
shim. It also fabricates marker executables instead of invoking a first-party producer.

The independent oracle closes the review gate's behavioral proof obligation, including the
real producer and installed shim, but it does not strengthen the tests that will remain in
the PR after merge.

### F4: the dependency-free launcher job sets up pnpm

The suite imports only Node builtins and `devDependencies` is empty. The workflow's existing
dependency-free sibling invokes Node directly, while jobs that set up pnpm also install
dependencies. Running through the package script is defensible, so this is nit-tier.

## Corrected attribution

The launcher-versus-shim divergence is real but is not introduced by this PR.

The external drive packed and installed the package globally twice. The installed `.cmd`
targets `agent-browser-win32-x64.exe`, while both x64 and arm64 executables exist. The
launcher selects arm64 in that same installed-tree state.

The critical correction is the base comparison: the base launcher also selects arm64 when
both files exist. The previous review used base's x64-only hard error to argue novelty in the
both-present state. Those are opposite preconditions. The divergence therefore moves from
an in-scope finding to an issue candidate, and assumption A6 is refuted.

## Additional issue candidates

1. **Native Windows ARM64 `agent-browser install` panics.** The source-built arm64 binary
   exited 101 at `cli/src/install.rs:181` with `Unsupported platform for Chrome for Testing
   download`. `run_install` guards Linux aarch64 only, while `platform_key()` lacks Windows
   aarch64. The emulated x64 image proceeds to download Chrome for win64. This predates the
   PR, but the binary the PR prefers cannot run `install` while the fallback can.
2. **Windows ARM64 is absent from advertised platform surfaces.** README and docs omit it,
   while the changelog records support through x64 emulation in #1269. Pre-existing.
3. **The Windows ARM64 resolution rule is triplicated.** Launcher, postinstall, and
   copy-native independently encode the mapping with no shared resolver. Pre-existing.
4. **cuse cannot install on `windows-11-arm64`.** Recorded as `crafter-agents/cuse#103`;
   the missing supported-runner contract is `crafter-agents/cuse#104`. A dedicated oracle
   workflow was used instead.
