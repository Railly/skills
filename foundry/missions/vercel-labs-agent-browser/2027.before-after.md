# 2027 before/after: wait --download after a failed move

Same scenario on both builds: click a download link, `wait --download <file-under-a-regular-file>`, then retry with a valid path. Fresh session and namespace per run.

| Step | Before (135fc2a8) | After (uncommitted fix) |
|---|---|---|
| Invalid destination | `✗ Failed to create download directory: File exists (os error 17)`, source kept | same |
| Retry, valid path | `✗ Operation timed out`, `out/` missing, source still in `dl/` | `✓ Download saved to …/out/report.bin`, contents `report` |
| Third wait | n/a | `✗ Operation timed out` (claimed once) |

A1 (completion left in the daemon receiver) has no stable CLI trigger, since it needs an event inside the liveness round trip. It is covered by `e2e_wait_download_claims_a_completion_left_in_the_daemon_receiver`, which calls the handler without the per-command drain: `Err("Timeout waiting for download")` before, ok after.

Follow-up, out of contract: the "Download completed but no file is at …" path keeps the claim, so a file that lands after the 1s poll cannot be retried. Not reproduced.
