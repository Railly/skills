## Findings

### Medium — `throw undefined` from `onData` is silently swallowed

`WTerm.write()` and `_drainResponses()` use `undefined` as both the “no delivery error” sentinel and a valid caught JavaScript value (`packages/@wterm/dom/src/wterm.ts:148-162,235-246`). If an `onData` handler executes `throw undefined`, the handler runs and all responses continue draining, but both `firstError ??= error` and `deliveryError !== undefined` treat the thrown value as absence. `write()` therefore returns normally instead of preserving the first consumer failure, contrary to the new error-isolation behavior for every other thrown value.

Confirmed through the built DOM package and committed WASM in Chromium: an `onData` callback ran, executed `throw undefined`, and `WTerm.write("\x1b[6n")` returned normally. Track presence separately from the error value, for example with a boolean or a tagged result, and add a regression cell for a falsy/non-`Error` thrown value.

### Medium — the new handler-error test does not verify render scheduling

The test is named `finishes parsing and schedules rendering when onData throws`, but its assertions cover only the rethrown error, both response callbacks, and `getResponse` call count (`packages/@wterm/dom/src/__tests__/wterm.test.ts:321-350`). In an isolated snapshot-restored clone, removing only `_scheduleRender()` from the error path left all 34 focused DOM tests green. A future regression can again parse the later chunk yet leave its completed screen update invisible, while the test claiming to guard that behavior passes.

Assert the rendered substrate after timers/RAF, or spy on the scheduling seam and force-red that assertion by removing `_scheduleRender()`.

## Adjacent-regression inspection

Queue enqueue/pop are O(1); draining is O(responses), and the 10,000-response drive completed without loss.
