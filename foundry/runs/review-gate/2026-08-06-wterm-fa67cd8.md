## Findings

### P1 — A single valid write can still overflow the queue and lose a response

`WTerm.write()` drains only after `bridge.writeString` / `writeRaw` returns (`packages/@wterm/dom/src/wterm.ts:146-156`). `WasmBridge.writeRaw()` processes arbitrary input in internal 8,192-byte chunks without exposing a drain point (`packages/@wterm/core/src/wasm-bridge.ts:112-120`), while the new core silently drops the newest response at 2,048 queued entries (`src/terminal.zig:281-287`).

Claim-layer reproduction against the built `WTerm` and committed PR WASM sent `"\x1b[6n".repeat(2049)` in one call: 8,196 input bytes and 2,048 `onData` callbacks. One valid CPR reply was silently lost. The adjacent layer assumed correct by the bounded FIFO is producer/consumer coordination across `WasmBridge`'s internal chunking; the PR does not coordinate capacity or drain between chunks.

### P1 — The DOM delivery fix has no force-red regression test

The edited response-forwarding test configures one response and asserts one callback (`packages/@wterm/dom/src/__tests__/wterm.test.ts:291-302`). It never exercises the new loop, multiple replies, or immediate draining from `write()`.

Force-red verification transpiled and drove `origin/main`'s pre-fix `WTerm` with two queued responses: it delivered only `response-a` and left `response-b` queued, yet the PR's current one-response test would still pass. The core FIFO test is valid and force-red: against `origin/main`'s committed WASM, the expected two replies became only the overwritten last reply (`["ESC[1;2R", null, null]`). Thus the producer fix is guarded, but the delivery fix is not.

### P2 — `getResponse()` API documentation still describes the retired single buffer

`apps/docs/src/app/api-reference/page.mdx:483-484` says, “Reading clears the buffer.” At PR HEAD each call pops only the queue head and leaves later pending responses intact (`WasmBridge.getResponse()` calls `clearResponse()`, whose WASM export now calls `popResponse()`). The sentence is stale and should describe dequeueing one pending response. This confirms the `siblings getResponse` obligation rather than exempting it.

## Subsystem model

- Producer: built-in Zig `handleDeviceStatus` creates CPR responses and enqueues them.
- Boundary: WASM exposes the queue head through `getResponsePtr/getResponseLen`; `clearResponse` now pops exactly one item.
- Consumer: `WasmBridge.getResponse()` decodes and consumes one item; `WTerm` drains and forwards through `onData`, which is also the keyboard-input channel consumed by React, Vue, PTY, WebSocket, and shell integrations.
- Alternate core: `GhosttyCore.getResponse()` remains a valid interface implementation but always returns `null` because its readonly stream cannot generate replies.
- Topology: all changed response delivery is in-process (Zig WASM → TypeScript bridge → DOM orchestrator → application callback); there is no detached process or separate stderr/log channel.
