## Findings, ordered by severity

### P1 — Default padding shifts mouse reports away from the clicked cell

`packages/@wterm/dom/src/input.ts:249-267` scales coordinates over `this.element.getBoundingClientRect()`. The `.wterm` root has 12px default padding, while `cols`/`rows` describe the content grid. A temporary built-package test drove `WTerm` with the committed core WASM and the default 80x24 content geometry: a click centered in content cell 1,1 (`clientX=27`, `clientY=40` for a 824x424 padded border box) emitted `ESC[<0;2;2M` and `ESC[<0;2;2m`, not 1,1. xterm's coordinate oracle explicitly subtracts `padding-left` and `padding-top` before dividing by cell dimensions.

The prior scrollback bug is fixed—the history-containing `.term-grid` is no longer the coordinate rectangle—but replacing it with the padded root created the inverse regression. Use the active content box: subtract computed padding/border and map using measured cell width/row height, without including scrollback rows.

### P2 — Mouse capture still breaks across valid browser/button lifecycles

`packages/@wterm/dom/src/input.ts:114-122,242-246,304-308` stores capture as one boolean and attaches listeners to module-global `window`. Three forced cells fail at the event-pipeline layer:

- A terminal element owned by an iframe document emits its press, but mouseup on `element.ownerDocument.defaultView` emits no release because listeners were attached to the outer window. xterm attaches to the element's current owner document specifically for moved/iframe terminals.
- Left+right chord: releasing right with `event.buttons=1` emits the right release and immediately removes capture; the later left release is lost. xterm retains global listeners until `event.buttons` reaches zero.
- A zero-geometry press arms capture before the rectangle guard returns. If geometry becomes valid before mouseup, WTerm emits an orphan release without a press.

Use the element's owning document/window, arm only after a press is valid and emitted, and keep capture until no buttons remain. The original prior finding's ordinary main-window, one-button outside release is fixed and force-red verified; these are adjacent regressions in the new capture implementation.

### P2 — Required web/root/Ghostty documentation is still missing

The follow-up correctly updates `packages/@wterm/core/README.md` and `packages/@wterm/dom/README.md`, including removing the false claim that mouse tracking requires Ghostty. However, the user-facing change still has no docs-app change and no root feature-list change. `apps/docs/src/app/api-reference/page.mdx` ends the WasmBridge mode table at `usingAltScreen()` and omits `mouseTracking()`, `mouseSgr()`, and `focusEvents()`; `apps/docs/src/app/vanilla/page.mdx` does not describe automatic mouse/focus `onData`; the root README feature list omits mouse/focus support; and `packages/@wterm/ghostty/README.md` does not document the new public mode accessors/parity.

After correcting the canonical surface-map syntax/globs, `gate.sh surfaces` flags the missing docs-app page and root README. This remains a repository-rule violation, not a release-note request.

## Subsystem model and adjacent layers

The terminal application writes DEC modes into either committed WASM core. `TerminalCore` exposes mode state to `InputHandler`; DOM mouse/focus events are encoded to `WTerm.onData`, which reaches the PTY transport. Pointer topology spans the terminal element, its owner document/window during capture, the active content-grid geometry, and possibly scrollback in the root scroller. Each fix assumed an adjacent layer: scrollback repair assumed root geometry was the grid; capture repair assumed global `window` and one pressed button; Ghostty parity assumed the committed binary matched Zig; package-doc repair assumed package READMEs were the full contract surface. The findings and artifact checks above test those assumptions.
