## Findings

### High — an `onData` exception truncates the remaining bytes of the same terminal write

`WTerm.write()` passes `() => this._drainResponses()` into `WasmBridge.writeString/writeRaw` (`packages/@wterm/dom/src/wterm.ts:149-151`). `WasmBridge.writeRaw()` invokes that callback synchronously after each 8,192-byte parser chunk and before processing the next one (`packages/@wterm/core/src/wasm-bridge.ts:112-121`). `_drainResponses()` calls the application's `onData` without isolating errors. If that callback throws, the exception exits the bridge loop, so later PTY bytes are never parsed and `_scheduleRender()` is never reached.

Forced through the built DOM package and committed WASM: the first 8,192-byte chunk was `"A".repeat(8188) + CSI 6 n`; the next chunk was `CSI H + "Z"`; `onData` threw `consumer failed`. The write threw, cell `(0,0)` remained `A`, and the cursor remained `(23,28)`. With the identical stream and a non-throwing consumer, cell `(0,0)` became `Z` and the cursor became `(0,1)`. Before this follow-up, response forwarding happened only after `writeString/writeRaw` returned, so a consumer exception could not discard unparsed input from the same write.

Handle consumer failures outside the parser loop (for example, drain into a temporary list between chunks and invoke user callbacks only after all input is parsed), or catch/report callback failures while guaranteeing remaining chunks and render scheduling still complete. Add a force-red test with a response in chunk one and observable terminal input in chunk two.

### Medium — the new public `afterChunk` callback is absent from both public API method tables

`TerminalCore` now exposes `writeString(str, afterChunk?)` and `writeRaw(data, afterChunk?)` (`packages/@wterm/core/src/terminal-core.ts:38-39`), and `WasmBridge` implements the public callback contract. The package README still lists `writeString(str)` and `writeRaw(data: Uint8Array)` (`packages/@wterm/core/README.md:59-60`), while the web API reference lists those same old signatures (`apps/docs/src/app/api-reference/page.mdx:447-452`). Neither explains that the callback runs synchronously after every internal 8,192-byte chunk, including the final chunk, or that its exception aborts the write. This is a public API change under the repository's documentation rule.

## Subsystem model and radius map

The PTY/browser transport calls `WTerm.write`, which streams bytes through `WasmBridge` in 8,192-byte chunks into the Zig parser. CPR production enqueues fixed-size response records in WASM. `WasmBridge.getResponse()` decodes and pops one record; `WTerm._drainResponses()` is the only built-in consumer and emits records through application `onData`. Rendering is scheduled only after `writeString/writeRaw` completes. There is one browser process and one WASM instance; there is no detached process or alternate response channel.

The change assumes the newly synchronous callback cannot throw, destroy the terminal, or re-enter writes; that user-callback layer is the adjacent seam. The queue also assumes per-chunk draining bounds occupancy below 2,048, and docs assume public method signatures stay aligned.

Radius indexed five changed TS symbols and eleven impacted items. The main convergence item was `wasm-memory-growth.test.ts`, reached from `TerminalCore` and `WasmBridge`; inspection and the full suite cleared the memory-growth invariant. The map materially under-covers the change: `2,518` unresolved calls versus `515` edges, and it cannot trace the Zig/WASM boundary. No finding was map-attributed; both came from full-pipeline exploration outside the map.
