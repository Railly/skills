## 0. Trigger

Fires under two clauses. These are fixes for findings from a previous review round, and the fix changes CLI-to-daemon ordering plus persistent diagnostic contracts.

## 1. Contract

Every public way to request strict session-to-tab binding must establish it before attachment can select or mutate a tab. Diagnostic and configuration artifacts introduced by binding may expose only their documented safe information.

The complete pre-proposal brief is preserved at `/tmp/solution-gate-agent-browser-1589/brief.md` for this machine run.

## 2. Confirmed defects

1. `--cdp` and `--auto-connect` send a preliminary `launch` envelope before the eventual action. The preliminary envelope omits `pinTab`.
2. `sanitize_url` preserves opaque URL paths. A `data:text/html,victim-secret` URL reaches both the `.target` file and a later `tab_gone` error.
3. `pinTab` is absent from both JSON Schema copies even though the parser and configuration docs support it.

One premise in the brief was disproved before synthesis: the schema files are not byte-identical at the reviewed head. Their `allowedDomains` and `idleTimeout` descriptions already differ.

## 3. Forward chains

### Proposal A: reuse existing ordering and state

Main chain:

1. A helper stamps the existing pin preference onto preliminary CDP and auto-connect launch envelopes. **Observed mechanism:** these envelopes currently omit the field.
2. `execute_command` applies `pinTab` before it computes `needs_launch` or calls `handle_launch`. **Observed.**
3. `handle_launch` connects, then calls `apply_tab_binding_on_attach`. **Observed.**
4. With `pin_tab=true` and no binding, `apply_tab_binding_on_attach` creates a fresh tab and persists it. **Observed in source and survived the direct-launch E2E.**
5. The eventual navigation operates on the fresh bound target while the daemon PID and shared target remain unchanged. **Inferred for the fix; this exact CLI regression remains an implementation test target.**

Helpful branch:

- Keeping `pinTab` outside `LaunchOptions` leaves the compatibility hash unchanged, so repeated compatible launches remain idempotent. **Observed mechanism, inferred outcome.**

Harmful branches:

- Stamping provider or local envelopes would change pin timing outside the confirmed attach bug. **Inferred.** Designed out by limiting the preliminary-envelope change to CDP and auto-connect.
- Allowing every `about:` URL would admit more than the required `about:blank`. **Inferred.** Designed out by allowing exactly `about:blank`.
- Enforcing whole-file schema equality would force unrelated description drift into this PR. **Observed.** Designed out with focused `pinTab` assertions.

### Proposal B: attachment plan, diagnostic type, migration

Main chain:

1. Flag resolution becomes `Option<bool>` and the daemon builds an attachment plan. **Proposed.**
2. Browser constructors accept the plan and delay target selection until binding policy resolves. **Inferred.**
3. Every attachment path gains a new internal contract and test matrix. **Inferred.**
4. The ordering property becomes explicit at the browser API boundary. **Inferred benefit.**
5. Existing attach machinery is replaced even though direct `launch` with `pinTab:true` already creates a fresh tab. **Observed premise, inferred over-reach.**

Diagnostic branch:

1. A diagnostic URL type normalizes all capture, persistence, load, and rendering paths. **Proposed.**
2. Loading an unsafe legacy file triggers an atomic rewrite. **Proposed.**
3. A read-only runtime directory can turn a diagnostic migration into an attach failure. **Inferred and admitted by the proposer.**
4. The read path now mutates disk even though no released migration requirement was established for this PR. **Inferred harmful branch.**

Schema branch:

1. One canonical schema is copied to both destinations. **Proposed.**
2. Existing unrelated description differences must be reconciled. **Observed.**
3. Review scope expands beyond `pinTab`, increasing S1 risk. **Inferred.**

## 6. Synthesis

**Kind: graft, dominated by Proposal A.**

### Chosen shape

1. Add one client helper that preserves the current three-way wire semantics:
   - `pinTab:true` when the resolved flag is enabled.
   - `pinTab:false` only for the existing explicit disable path.
   - Omit the field when no preference was expressed.
2. Reuse that helper for the eventual command, batch commands, and the preliminary `--cdp` and `--auto-connect` launch envelopes. Do not add `pinTab` to `LaunchOptions` or the launch compatibility hash. Do not change provider or local launch timing in this review fix.
3. Reuse the daemon's current early `pinTab` handler and `apply_tab_binding_on_attach`. No attachment plan, new round trip, or browser constructor redesign.
4. Change `sanitize_url` to allow only:
   - sanitized HTTP and HTTPS scheme, host, explicit port, and path;
   - exactly `about:blank`;
   - empty for opaque, unsupported, or malformed URLs.
5. Apply the sanitizer at persistence and at both in-memory `tab_gone` capture paths: missing persisted target and live target removal. This includes defense against an old unsafe binding when it is converted to live diagnostic state, without making load perform a mandatory disk rewrite.
6. Add `pinTab` as a boolean beside `autoConnect` in both schema files. Add focused tests that assert presence, type, and matching property definitions in both files. Do not add a global byte-equality gate in this PR.

### What came from Proposal B

- Exact `about:blank`, rather than Fable's broader `about:` allowance.
- Explicit recognition that load/capture and error formatting are separate disclosure paths.
- The test requirement that the strict attach observable include unchanged PID, unchanged shared target, distinct bound target, and persisted `pinned:true`.

### Rejected material

- Attachment-plan redesign: direct launch with early `pinTab` already satisfies the browser-side property.
- `Option<bool>` flag redesign: broader than the confirmed omission and risks changing config/env false semantics.
- Mandatory lazy disk rewrite: creates attach failures in read-only directories without an established released migration need.
- Whole-schema canonicalization and byte equality: current unrelated drift makes it a separate cleanup.

## 7. Carried assumptions and implementation verification targets

1. Config/environment source semantics remain exactly as currently resolved by `Flags`; this fix transports the resolved preference earlier but does not redefine false-versus-absent.
2. Only preliminary CDP and auto-connect envelopes need changed timing for the reproduced shared-browser class.
3. Sanitizing a loaded URL when it enters `bound_target_gone` is sufficient for old-file disclosure defense; no on-load disk migration is required for this unmerged feature.
4. Add exact force-red tests:
   - already-running daemon, no binding, CDP, explicit true;
   - same through auto-connect;
   - existing sticky pin, preliminary launch, explicit false;
   - absent preference preserves sticky state;
   - `data:`, `blob:`, `javascript:`, `file:`, and non-blank `about:` are omitted;
   - HTTP(S) credentials/query/fragment are stripped while port/path remain;
   - exact `about:blank` remains;
   - persisted and live-removal `tab_gone` paths cannot disclose the secret;
   - both schemas expose matching boolean `pinTab`.
5. Review Gate must drive every item from the original must-not-change list, especially compatibility hash stability, repeated launch idempotency, provider/local behavior, atomic binding writes, and permissive Draft 7 schema behavior.

## 8. Separate cleanup candidate

The two published schema files have pre-existing description drift. Canonical generation or byte-for-byte enforcement is worthwhile, but it should be a separate change with its own decision about which descriptions are authoritative.
