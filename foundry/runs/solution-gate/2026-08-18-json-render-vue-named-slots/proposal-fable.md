1. **Shape**

Ownership stays entirely inside `packages/vue`; core, React, and shared contracts are untouched.

- `ElementRenderer` (`packages/vue/src/renderer.ts:398-440`) owns resolving `element.slots` (`packages/core/src/types.ts:68`) into per-name VNode lists and delivering them as additional entries in the Vue slots object it already passes — today it passes only `{ default: () => childrenVNodes }` (`packages/vue/src/renderer.ts:439`). Missing slot references reuse the existing children policy: silent while `loading`, location-specific warning after (`packages/vue/src/renderer.ts:410-416`, mirroring React's slot-aware message at `packages/react/src/renderer.tsx:425-433`).
- Raw registry components consume named content through Vue's native slot channel (the same slots object), so a plain Vue component's `<slot name="header">` outlet works with no new props. This satisfies the reconciled decision that authors get Vue-native slot functions.
- `defineRegistry`'s component wrapper (`packages/vue/src/renderer.ts:849-858`) owns exposing the received Vue `Slots` object in the render-function context while preserving the existing `children: slots.default?.()` alias. `BaseComponentProps` (`packages/vue/src/catalog-types.ts:58-72`) owns the corresponding type addition; its render contract (`packages/vue/src/renderer.ts:783-790`) gains a slots field typed as Vue slot functions.
- `defineRegistry` also owns registering catalog slot metadata against the registry — the Vue equivalent of React's `WeakMap` channel (`packages/react/src/renderer.tsx:92-94,816-821`) — so `ElementRenderer` can warn on `slots.default` and undeclared names with React's semantics (`packages/react/src/renderer.tsx:406-420`): warn, render undeclared names anyway, and let `children` win exclusively over `slots.default`.
- `packages/vue/src/schema.ts:13-30` owns the element-level `slots` opt-in (mirroring `packages/react/src/schema.ts:25`) plus a NAMED SLOTS generation rule (mirroring `packages/react/src/schema.ts:84`), which flips core's `supportsNamedSlots` prompt gate (`packages/core/src/schema.ts:677,830-851`). The catalog-side `slots: string[]` capability already exists (`packages/vue/src/schema.ts:39-40`).
- Repeat ownership does not move: `RepeatChildren` iterates only `children` (`packages/vue/src/renderer.ts:527-549`), so named slots render once at the owner's pre-repeat scope, matching the validator (`packages/core/src/spec-validator.ts:289-298`).
- Docs owned by the change: `packages/vue/README.md`, `skills/vue/SKILL.md`, and the Vue pages under `apps/web/`.

2. **Predictions**

1. `pnpm vitest run packages/vue` with a new test — catalog component declaring `slots: ["default", "header", "footer"]`, spec element with `children` plus `slots: { header: [...], footer: [...] }`, mounted via `@vue/test-utils` — shows header and footer content in their regions and children in the default region, through both a raw component registry and `defineRegistry` (parity with `packages/react/src/renderer.test.tsx:53-90`).
2. Same command, a console.warn spy: a spec using `slots.default` through `defineRegistry` produces one warning matching React's wording pattern (`packages/react/src/renderer.tsx:410-413`) and the default region contains only `children` content; an undeclared slot name warns but its content is still present in the DOM.
3. Same command, missing-reference test: an element whose `slots.header` names a nonexistent key produces zero warnings when `loading: true` and exactly one warning naming the slot and owner type when `loading: false`.
4. Same command, repeat test: an owner with `repeat` over a three-item array plus `slots.header` renders its child three times and the header exactly once, with no repeat item scope inside the header subtree (runtime counterpart of `packages/core/src/spec-validator.test.ts:327-353`).
5. After the schema opt-in, generating a prompt from a Vue catalog whose component declares a `header` slot includes `slots: header` in the AVAILABLE COMPONENTS line (measured by asserting on the generated prompt string; the gate is `packages/core/src/schema.ts:677,833-844` — today it prints only "accepts children").
6. `pnpm type-check` passes, and the full pre-existing Vue suite (`packages/vue/src/renderer.test.ts`, `hooks.test.ts`, composable tests) passes unmodified, evidencing children-only compatibility.

3. **Cost**

Moderate and localized: one rendering path and one warning block in `packages/vue/src/renderer.ts`, a metadata channel plus context field in `defineRegistry`, one type addition in `catalog-types.ts`, one schema line plus one rule in `schema.ts`, new tests, and three documentation surfaces (package README, `skills/vue/SKILL.md`, web docs). No core, React, or shared-contract changes; no new dependencies.

4. **What it makes worse**

- Prompt output changes for every existing Vue catalog (slot capability advertising turns on), so models begin emitting `slots` — apps that regenerate prompts while pinned to an older `@json-render/vue` get specs whose named content is silently dropped, since the old renderer reads only `children` (`packages/vue/src/renderer.ts:398-440`).
- Raw Vue components that already define internal named slots start receiving spec-driven content on those names; previously they could only ever receive `default` (`packages/vue/src/renderer.ts:439`).
- Warning coverage becomes uneven: metadata-backed `slots.default`/undeclared-name warnings only fire for registries built by `defineRegistry`, as in React (`packages/react/src/renderer.tsx:92-94,406-420`); raw registries render undeclared names silently.
- Two ways to reach default content coexist in `defineRegistry` contexts (the `children` alias and the native default slot function), which authors can conflate.
- Slightly more work per element carrying `slots` (building extra VNode lists), and larger prompts.

5. **Rejected alternatives**

- **Abstract `Record<string, VNode[]>` prop, mirroring React's `slots` component input** (`packages/react/src/catalog-types.ts:63`): rejected by the reconciled decision that authors consume Vue-native slot functions, and by the fact that raw Vue components receive content only through Vue's slot channel today (`packages/vue/src/renderer.ts:430-440`) — a prop cannot reach a plain component's `<slot name>` outlets.
- **Merging `slots.default` with `children`**: rejected by the reconciled "children wins exclusively" decision, React's explicit warning against `slots.default` (`packages/react/src/renderer.tsx:410-413`), and the schema rule "Never use `slots.default`" (`packages/react/src/schema.ts:84`).
- **Rejecting or refusing to render undeclared slot names**: rejected by React's established warn-and-render tolerance — it warns (`packages/react/src/renderer.tsx:414-418`) but still renders every `slots` entry (`packages/react/src/renderer.tsx:462-469`) — which the reconciled contract adopts.
- **Letting named slots inherit the owner's repeat scope**: rejected by core semantics — slot children are validated with the pre-repeat scope (`packages/core/src/spec-validator.ts:289-298`), the test asserting `$item` inside a named slot is out of scope (`packages/core/src/spec-validator.test.ts:327-353`), and `RepeatChildren` iterating only `children` (`packages/vue/src/renderer.ts:527-549`).
- **Supporting slots only through `defineRegistry`, not the low-level `Renderer`**: rejected because `ElementRenderer` is the only place spec references become VNodes (`packages/vue/src/renderer.ts:398-440`), and the reconciled observable requires raw registries to work.
- **Skipping the element-schema opt-in**: rejected because core gates all slot advertising on element-level `slots` presence (`packages/core/src/schema.ts:677`); without it Vue's spec schema (`packages/vue/src/schema.ts:13-30`) never describes the field and generation can never produce it.
