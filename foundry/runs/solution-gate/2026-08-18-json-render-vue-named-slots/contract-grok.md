## 1. Property

For any shared `UIElement`, Vue must treat `children` as default-slot content and `slots` as separately named content of the same element, so every named-slot descendant that core already stores, validates, reaches, autofixes, and flattens is actually rendered into the registered Vue component. Default content stays on Vue’s default slot; named content is not folded into `children`. `repeat` on the owning element still expands only `children` and does not put named-slot descendants into that repeat scope.

Evidence: shared shape `packages/core/src/types.ts:58-80`; nested flattening `packages/core/src/types.ts:685-768`; validation/reachability/autofix `packages/core/src/spec-validator.ts:134-146,289-292,324-330,492-512` and `packages/core/src/spec-validator.test.ts:62-75,167-182,327-345,589-608`; React already splits the two channels `packages/react/src/renderer.tsx:406-481`; Vue currently resolves only `children` and passes that as Vue’s default slot `packages/vue/src/renderer.ts:398-440`; Vue `defineRegistry` unwraps only `slots.default` `packages/vue/src/renderer.ts:849-858`; Vue catalog already declares `slots: string[]` but Vue spec schema has no element-level `slots` map `packages/vue/src/schema.ts:13-45`.

## 2. Observable success condition

A Vue tree whose spec has both `children` and named `slots` shows default descendants in the default slot and each named key’s descendants in that named channel, without moving named content into `children`. A children-only spec still renders exactly as today. A nested spec converted to flat still carries `element.slots` as string-key maps, and Vue then renders those keys. Missing slot refs stay silent while `loading` is true and warn (without throwing) after load. Repeat on the owner still repeats only `children`; named-slot content of that owner is not given the owner’s repeat `$item` scope.

Evidence of the intended split: React `packages/react/src/renderer.test.tsx:53-106` (`header`/`footer` via `slots`, main via `children`); React renderer `packages/react/src/renderer.tsx:422-481`; nested→flat `packages/core/src/types.test.ts:829-847` and React stream preservation `packages/react/src/hooks.test.ts:314-336`; missing-ref loading gate `packages/react/src/renderer.tsx:425-433` and Vue children analogue `packages/vue/src/renderer.ts:408-416`; repeat-scope rule `packages/core/src/spec-validator.ts:281-297` and `packages/core/src/spec-validator.test.ts:327-352`; Vue children-only success today `packages/vue/src/renderer.test.ts:97-112,149-165`. Vue has no named-slot renderer test; `packages/vue/src/renderer.ts:398-440` never reads `resolvedElement.slots`.

## 3. Must not change

- Default content remains `UIElement.children` and continues to be passed as Vue’s default slot `{ default: () => childrenVNodes }` (`packages/vue/src/renderer.ts:398-440`). Product ask: keep the current default-child API.
- `defineRegistry` authors still receive evaluated default content as `children?: VNode | VNode[]` from `slots.default?.()` (`packages/vue/src/catalog-types.ts:58-72`; `packages/vue/src/renderer.ts:783-790,849-858`; `packages/vue/README.md:56-72,364-375`).
- Low-level registry components remain Vue components that read default content from Vue’s `slots.default`, not from a `children` prop (`packages/vue/src/renderer.ts:65-84`; `packages/vue/src/dynamic-forms.test.ts:22-77`).
- `repeat` still repeats only `children` (`packages/vue/src/renderer.ts:399-406,528-549`; React same split `packages/react/src/renderer.tsx:449-469`). Core still requires repeat to have children and still withholds the owner’s repeat scope from named slots (`packages/core/src/spec-validator.ts:149-157,281-297`; `packages/core/src/spec-validator.test.ts:327-352`).
- Shared spec type, validator, autofix, prompt gating, and `nestedToFlat` stay owned by core (`packages/core/src/types.ts:58-80,726-768`; `packages/core/src/spec-validator.ts:134-146,324-330,492-512`; `packages/core/src/schema.ts:677,830-851`).
- Existing Vue `ComponentRenderProps` (`element`, `emit`, `on`, `bindings`, `loading`) stay the low-level prop surface (`packages/vue/src/renderer.ts:65-78`). Catalog `slots: string[]` remains a capability declaration (`packages/vue/src/schema.ts:39-40`).
- Children-only rendering, fallback, loading passthrough, and event emit behavior covered by `packages/vue/src/renderer.test.ts` stay intact.

## 4. Boundaries

**Trust.** Catalog `slots: string[]` is the declared capability (`packages/vue/src/schema.ts:39-40`; `packages/core/src/schema.ts:1162-1166`). Spec `slots?: Record<string, string[]>` is untrusted generated content (`packages/core/src/types.ts:68`). React consults catalog metadata only when present and then warns on `slots.default` and undeclared names, while still rendering (`packages/react/src/renderer.tsx:92-95,406-419,462-481,816-821`). Vue has no `registryMetadata` and `defineRegistry` discards the catalog at runtime (`packages/vue/src/renderer.ts:817-821`). Runtime policy for undeclared names is not fixed in Vue.

**Authority.** Shared `UIElement` is the structural source of truth (`packages/core/src/types.ts:58-80`). Vue’s spec schema currently omits element-level `slots` (`packages/vue/src/schema.ts:17-29`), so Vue catalogs do not advertise named slots in prompts (`packages/core/src/schema.ts:677,830-844`). React schema does accept the map and injects a `NAMED SLOTS` rule (`packages/react/src/schema.ts:25,79-84`). Core `validateSpec` / `autoFixSpec` already treat slot refs as first-class (`packages/core/src/spec-validator.ts:134-146,492-512`; `packages/core/README.md:559-561`). React README still calls element `slots` a React-only feature (`packages/react/README.md:125-130`); Vue README’s `UIElement` omits it (`packages/vue/README.md:121-136`).

**Ownership.** Core owns storage, reachability, flattening, and prompt gating. Vue renderer owns resolving keys to VNodes and delivering them through Vue’s slot object (`packages/vue/src/renderer.ts:398-440`). Catalog components own where slot content is placed: `defineRegistry` fns today only see `children` (`packages/vue/src/renderer.ts:849-858`); low-level Vue components own Vue `slots` (`packages/vue/src/dynamic-forms.test.ts:75-76`). Repeat scope is owned by `RepeatChildren` + `RepeatScopeProvider` and applies only to `element.children` (`packages/vue/src/renderer.ts:466-552`).

**Lifecycle.** Slot and child keys are resolved at render time against `spec.elements`. Missing keys: no warn while `loading` is true; warn and skip after load (`packages/vue/src/renderer.ts:408-416` for children; React extends the same gate to named slots with a slot location string `packages/react/src/renderer.tsx:422-433`). During streaming, nested parts may already carry named slots (`packages/react/src/hooks.test.ts:314-336`; `packages/core/src/types.ts:726-768`). Visibility is evaluated per `ElementRenderer` (`packages/vue/src/renderer.ts:370-376`), so slot descendants would inherit that lifecycle only if they are rendered through `ElementRenderer` as children are.

**Compatibility.** Vue must keep Vue-native default-slot delivery (`packages/vue/src/renderer.ts:430-440`) rather than React’s `children` + `slots` props (`packages/react/src/renderer.tsx:60-65,471-481`; `packages/react/src/catalog-types.ts:60-74`). `defineRegistry` vs raw `ComponentRegistry` are different author APIs (`packages/vue/src/renderer.ts:65-84,783-860`). Svelte/Solid schemas also omit element `slots` (`packages/svelte/src/schema.ts:17-29`; `packages/solid/src/schema.ts:17-29`); this task is Vue parity with the shared spec, not a claim that every renderer already renders named slots.

| **missing referenced element while loading and after loading** | Children: skip, warn only when `!loading` (`packages/vue/src/renderer.ts:408-416`; React `packages/react/src/renderer.tsx:425-433`). ## 6. Blocking unknowns

- Runtime policy for undeclared slot names: reject, warn, or render. React warns and renders when catalog metadata exists (`packages/react/src/renderer.tsx:407-419,462-469`); Vue has no equivalent metadata (`packages/vue/src/renderer.ts:817-821`). Packet marks this unknown.
- Author consumption API for named slots: abstract `Record<string, VNode[]>`, Vue-native slot functions on the `h()` third argument / `setup(_, { slots })`, or something else. React chose a `slots` prop (`packages/react/src/catalog-types.ts:60-74`; `packages/react/src/renderer.tsx:471-481`). Vue today is Vue-native for default only (`packages/vue/src/renderer.ts:430-440,849-858`; `packages/vue/src/catalog-types.ts:58-72`). Packet marks this unknown. Until it is fixed, `defineRegistry` vs low-level registry cannot be specified beyond “default children stay as they are.”
- `slots.default` at runtime: warn-and-keep-separate (React `packages/react/src/renderer.tsx:409-413,462-468`), merge into Vue default, or drop. Schema/prompt say never use it (`packages/react/src/schema.ts:84`); Vue schema is silent (`packages/vue/src/schema.ts:78-96`).
- Whether Vue’s spec schema must gain an optional element `slots` map (as React `packages/react/src/schema.ts:25`) so `supportsNamedSlots` becomes true for Vue catalogs (`packages/core/src/schema.ts:677,830-844`). Without that, even a correct renderer would still generate prompts that hide named slots.
- Whether Vue should attach catalog slot metadata on `defineRegistry` / `createRenderer` the way React does (`packages/react/src/renderer.tsx:816-821,955-960` vs `packages/vue/src/renderer.ts:817-821,951-959`), which is required before React’s warn path can be a Vue observable.
