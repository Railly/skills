wterm #118 fractional scroll ownership

Solution Gate on main at 4a73024, August 13, 2026.

Observed behavior

Current ownership failure

external observation Electron/Linux requested bottom 7556 and landed near 7555.

Exact equality classified wterm's own scroll as user movement and disabled following.

Browser assignments

observed At DPR 1.25, targets 100.25 and 100.5 were accepted as 100 and 101.

Requested values are not stable ownership tokens.

Second clamp

observed Assignment landed at 900, layout changed, then the event arrived at 899.

This refutes read-back plus strict event equality.

Event semantics

observed No-op assignments emit no event. Three writes coalesced into one event. Programmatic events were trusted.

Boolean, counter, and isTrusted designs do not identify ownership.

Proposed shapes

This half is argument. Evidence marks do not turn proposals into observations.

Fable: accepted value, strict event

inferred assign → read accepted value → exact event match

refuted Layout can re-clamp before event delivery.

Useful contribution: one helper owns every product scroll write.

Graft: accepted token plus bounded event distance

inferred request past end → browser chooses true maximum

inferred record accepted position → consume event within one CSS pixel

inferred single-use token → bounded attribution

Accepted cost: a one-pixel concurrent user movement may be consumed. Existing bottom semantics already use a five-pixel following band.

Implementation contract

  1. _scrollToBottom assigns scrollHeight and lets the browser clamp.
  2. _setScrollTop records the accepted value only when the position moves.
  3. _onScroll consumes one event within one CSS pixel of the token.
  4. A non-match clears the token, disables following, and schedules rendering.
  5. Every product scrollTop write uses the helper.
  6. Resize-pending ownership remains higher priority.
