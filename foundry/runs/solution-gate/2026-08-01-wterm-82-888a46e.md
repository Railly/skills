# Solution gate: vercel-labs/wterm#82 — GhosttyCore.load() fails under Bun's dev server

Date: 2026-08-01. Target commit `888a46e`.
Proposers: `fable-5` (A), `gpt-5.6-sol` @ high (B), in isolated clones under `~/Programming/vercel/_sg82/{p1,p2}`.
Synthesis/implementation: `claude-opus-5`.

## Step 0 — Trigger

Fires: more than one solution shape (where the default URL comes from), and it changes the contract between the package and the consumer's bundler.

## Step 1 — Defect as contract

**Property violated.** The default entry point produces a resource URL that is only valid on the machine that compiled it. A bundler that inlines the module resolves `import.meta.url` at build time to the source file on disk, baking a `file://` URL into a browser bundle.

**Observable.** `GhosttyCore.load()` with no arguments either works, or fails with an error naming the cause and the remedy. `Failed to fetch` is neither.

**Must not change.** The `wasmPath` escape hatch; Node/vitest suites; the committed binary and its build script; `@wterm/core`'s strategy.

## Step 2 — Proposals

| | A (fable-5) | B (gpt-5.6-sol) |
|---|---|---|
| Default URL | keep `new URL("../wasm/...", import.meta.url)`, moved into the function body so it evaluates lazily | replace with a same-origin literal `/ghostty-vt.wasm` |
| Who owns it | the consumer's bundler, when it understands the pattern; the consumer via `wasmPath` when it does not | always the consumer, who must deploy the asset at the default path |
| Failure | throw before fetching when the resolved default is `file:` in a browser-like env; check `response.ok` and the `\0asm` magic bytes | throw with attempted URL, cause and remedies on any non-OK |
| Package surface | add `"./ghostty-vt.wasm"` subpath export | add `@wterm/ghostty/wasm` subpath export |

Both rejected base64 inlining for the same reason, and both landed on a subpath export.

## Step 3 — Probe log

**P1 — does the default work under Vite dev?** Ran the repo's own `examples/ghostty` (which calls `GhosttyCore.load()` with no argument) and drove it with Playwright.
```
wasm requests: http://localhost:5188/@fs/.../packages/@wterm/ghostty/wasm/ghostty-vt.wasm
errors: none          terminal rendered: true
```
→ **Works.** Vite dev serves the file over HTTP.

**P2 — does it survive a Vite production build?**
```
$ npx vite build
dist/assets/ghostty-vt-DiZajRMV.wasm      <- emitted, content-hashed
$ grep -c "file://" dist/assets/*.js  ->  0
$ vite preview + Playwright
wasm requests: http://localhost:5189/assets/ghostty-vt-DiZajRMV.wasm
errors: none          terminal rendered: true
```
→ **Works, and correctly.** `new URL(..., import.meta.url)` is the pattern Vite/Rollup implement.

**This refutes B's premise.** B replaces a default that already works zero-config on Vite with one that requires every consumer to copy an asset. See S1 below.

**P3 — A's load-bearing claim: does Vite still rewrite the URL from inside a function body?** Applied A's exact restructuring to `wasm-bindings.ts` and rebuilt.
```
dist/assets/ghostty-vt-DiZajRMV.wasm      <- still emitted
grep -c "file://"  ->  0
```
→ **Survives.** A's lazy move is safe. File restored afterward.

**P4 — Bun.** Reproduced the report on Bun 1.3.14 with a linked workspace copy, in Chromium:
```
PAGE: FAILED: Failed to fetch
console: Fetch API cannot load file:///Users/.../wasm/ghostty-vt.wasm.
         URL scheme "file" is not supported.
```
→ Confirmed, and sharper than the issue's own wording: it is a build-time absolute path escaping into a runtime fetch, not an unresolved file.

**P5 — the premise nobody checked, including me.** The issue says "This works in Next.js (which the examples use)", and I repeated it in the brief. False:
```
examples/local/package.json predev/prebuild:
  cp node_modules/@wterm/ghostty/wasm/ghostty-vt.wasm public/ghostty-vt.wasm
examples/local/app/ghostty/page.tsx:
  GhosttyCore.load({ wasmPath: "/ghostty-vt.wasm" })
```
The Next example never exercises the default. It copies the binary into `public/` and passes an explicit path. So Next is not evidence about the default in either direction, and the only in-repo consumer of the default is the Vite example.

**Unprobed.** esbuild (binary not installed), Rollup without Vite, Parcel, webpack standalone, and whether A's magic-byte check can reject a working exotic setup. Recorded as assumptions, not upgraded to facts.

## Step 5 — Synthesis: A whole, one graft, one correction

**Take A's shape.** Keep the `new URL(..., import.meta.url)` literal, evaluated lazily inside the loader. Add the pre-fetch guard, the `response.ok` check and the magic-byte check. Add the subpath export. Add a bundlers section to the README.

**Graft from B: the support-matrix discipline.** B was stricter about not claiming coverage it had not tested. The docs state exactly what is verified (Vite dev and build, Bun as a documented failure with a remedy) and name the rest as unverified rather than implied.

**Reject B's default change**, refuted by P1 and P2: it fixes the minority by regressing the majority.

**Correction carried into implementation:** the Next recipe (copy to `public/`, pass `wasmPath`) is already the documented fallback pattern in this repo's own example. That, not a new invented convention, is what the README should show for bundlers that do not implement the URL pattern.

## Carried assumptions

1. esbuild, Rollup-standalone, Parcel and webpack-standalone behavior. Unprobed.
2. The magic-byte check rejects nothing that works today.
3. The `file:` + `document` guard's false-positive set is limited to jsdom/happy-dom and Electron `file://` renderers.

## Must-not-change list → Review Gate step 5

- `examples/ghostty` under Vite dev and `vite build` + `preview`, driven in a browser, still loads with no `wasmPath`.
- `examples/local` under Next still loads with its explicit `wasmPath`.
- `pnpm --filter @wterm/ghostty test` and `type-check`, unchanged, with no test edits.
- The JS bundle gains no wasm bytes: no `AGFzbQ` base64 in `dist`.

## Issue candidates found by probing

1. The issue's Next.js claim is wrong; worth correcting on #82 so the next person does not design against it.
2. `examples/local`'s manual copy step is the de-facto supported recipe and is not documented anywhere outside that example's `package.json`.

## Outcome

Shape decided. The gate's value here was one probe: running the repo's own Vite example proved the default already works where it was assumed broken, which turned the better-argued proposal into the one that would have caused a regression.
