## 0. Trigger

The gate fires under two clauses. The defect admits incompatible ownership and lifecycle shapes, and the fix introduces a persistent contract shared by the CLI, daemon, Chrome, and state storage.

## 1. Contract

Property:

> Each isolation boundary sharing one Chrome must exclusively own its storage and targets throughout its lifecycle.

Observable:

> Two boundaries using the same origin in one Chrome retain separate cookies and storage. Creating, listing, reconnecting, and closing one boundary neither adopts nor destroys targets owned by the other.

Must not change:

- behavior without isolation
- named sessions and `--pin-tab`
- local profile workflows
- target references
- compatibility with existing state files
- workflows that deliberately share one login

## 2. Current subsystem facts

1. `BrowserManager::discover_and_attach_targets` calls browser-wide `Target.getTargets` and attaches every page or webview. There is no BrowserContext ownership filter.
2. `TargetInfo` already includes `browser_context_id`.
3. `--pin-tab` binds one target but does not partition cookies or storage.
4. `Network.getAllCookies`, cookie mutation, and storage commands run through the active page session.
5. `state save` collects additional origins through a temporary target created in the default BrowserContext.
6. Browser-level `Target.setAutoAttach` can attach and pause targets created inside another BrowserContext.
7. Internal daemon restart and explicit user `close` currently share teardown helpers.
8. The recording flow already creates a secondary BrowserContext and replays download and certificate settings into it.
9. `{session}.target` is atomic, owner-only, fsynced, and intentionally survives daemon restarts.

## 3. Forward chains

### Proposal A

Main chain:

1. `--isolated` selects a session-owned BrowserContext. **Proposed.**
2. The context id is persisted with the target binding. **Inferred from the existing atomic sidecar.**
3. Reconnect enumerates contexts and targets, then attaches only matching targets. **Inferred.**
4. Target commands and page events remain within that context. **Inferred.**
5. Explicit close disposes the context atomically. **Observed CDP mechanism, inferred integration.**

Helpful branch:

- Chrome owns cookie and storage partitioning, so agent-browser does not emulate isolation in application code. **Observed in the real-Chrome probe.**

Harmful branches:

- Treating every daemon shutdown as boundary close disposes the context during a normal daemon restart. **Observed in current lifecycle code.**
- Filtering discovery but not browser-level auto-attach allows an isolated daemon to pause and configure foreign targets. **Observed in the real-Chrome auto-attach probe.**
- A hard `context_gone` after Chrome restart exposes a Chrome implementation id as a permanent user identity and blocks existing restore recovery. **Inferred from current restore behavior.**
- Optional fields readable by an older binary allow a downgrade to silently lose target filtering. **Inferred from serde's unknown-field behavior.**

### Proposal B

Main chain:

1. `--isolate-context` selects an owned context set. **Proposed.**
2. A primary context owns normal tabs while special features can register child contexts. **Inferred.**
3. Every discovery, creation, event, state, and teardown path applies the same ownership predicate. **Inferred.**
4. Reconnect validates the context and restores the bound target. **Inferred.**
5. Close disposes owned contexts and leaves foreign targets intact. **Observed CDP mechanism, inferred integration.**

Helpful branch:

- The proposal names recording and state temporary targets, two consumers a single-context sketch can miss. **Inferred from source trace.**

Harmful branches:

- A browser fingerprint and general owned-context set add contract surface before the product supports user-managed context collections. **Inferred.**
- Losing the sidecar can orphan a context until Chrome exits. **Inferred.**
- Registering a context after a target-producing feature runs creates a race where foreign event handlers see the target first. **Inferred.**
- Reusing the current generic close path would dispose contexts on internal restart. **Observed integration seam.**

## 4. Probe log

### Probe 1: storage and target partitioning

Command:

```bash
bun /tmp/agent-browser-1068-cdp-probe.mjs
```

Observed against Chrome 151:

- Context A read cookie, localStorage, and sessionStorage value `A`.
- Context B read value `B` for the same origin.
- `Network.getAllCookies` on A returned only A's cookie; B returned only B's.
- Browser-wide `Target.getTargets` returned targets from all three contexts with `browserContextId`.
- Normal contexts survived closing the browser CDP socket.
- A context created with `disposeOnDetach:true` disappeared with its target when that socket disconnected.
- Reattaching to A after daemon-like disconnect preserved A's storage.
- Disposing A removed A's target and preserved B's.

Disposition:

- BrowserContext as the isolation primitive: survived.
- `disposeOnDetach:true`: refuted because daemon restart must preserve the boundary.
- Browser-wide discovery without filtering: refuted.

### Probe 2: browser-level auto-attach crosses contexts

Command:

```bash
bun /tmp/agent-browser-1068-autoattach-probe.mjs
```

Observed:

```json
{
  "observerReceivedForeignAttachment": true,
  "waitingForDebugger": true
}
```

A CDP client with browser-level `Target.setAutoAttach` received and paused a target created by another client in another BrowserContext.

Disposition:

- Filtering only `Target.getTargets` and `tab list`: refuted.
- Ownership must be checked before registration, network controls, navigation, or close.
- Foreign auto-attached sessions must be immediately resumed and ignored, or isolated mode must avoid browser-wide auto-attach where possible.

### Probe 3: state temporary target

Source observation:

```text
cli/src/native/state.rs: collect_storage_via_temp_target
Target.createTarget({url:"about:blank"})
```

The temporary target currently omits `browserContextId`.

Disposition:

- Reusing state save unchanged: refuted for multi-origin localStorage.
- The existing state JSON shape can remain unchanged, but every temporary target must be created inside the owned context.

### Probe 4: lifecycle split

Source observation:

- explicit `close` calls `handle_close`
- internal daemon shutdown also calls `handle_close`
- idle and signal shutdown call `close_all_browser_backends`

Disposition:

- Adding context disposal to `BrowserManager::close` or generic teardown: refuted.
- The implementation needs separate detach and boundary-close semantics.

### Probe 5: recording and secondary contexts

Source observation:

- recording creates another BrowserContext
- it manually reapplies download behavior and certificate settings

Disposition:

- "Exactly one context exists" is too narrow for all current features.
- The public boundary owns one primary context. Any internal child context must be registered before its targets are exposed and disposed by the feature or explicit boundary close.

### Probe 6: persistence and downgrade

Source observation:

- `.target` writes are atomic and survive daemon restarts
- legacy `TabBinding` ignores unknown fields

Disposition:

- Reusing one sidecar: survived.
- Adding optional isolation fields to the legacy shape: refuted as fail-open on binary downgrade.
- Isolated bindings need a versioned representation that pre-isolation binaries cannot parse, while the new loader remains backward-compatible with legacy bindings.

## 6. Synthesis

Kind: graft. Both proposals converge on the primary shape. Proposal A supplies the minimal session-owned boundary. Proposal B supplies the complete consumer set. The probes add lifecycle, downgrade, and auto-attach requirements neither proposal fully handled.

### Chosen shape

1. Add explicit `--isolate-context` and `AGENT_BROWSER_ISOLATE_CONTEXT` support for shared Chrome connections (`--cdp`, `--auto-connect`, and `connect`). Do not make isolation the default.
2. A named agent-browser session owns one primary Chrome BrowserContext. The session name is the user identity; a second context name is redundant.
3. The first isolated attach creates the context and an `about:blank` target. It never adopts a default-context target.
4. Persist the isolation mode, primary `browserContextId`, bound target, pin state, and safe URL in the existing atomic binding file.
5. Use a versioned isolated-binding representation that old binaries fail to parse. The new loader accepts both legacy bindings and the new isolated shape. Downgrade must fail closed instead of silently losing isolation.
6. A daemon restart detaches only. It leaves the BrowserContext and binding intact. Reconnect calls `Target.getBrowserContexts`, filters `Target.getTargets` by `browserContextId`, then restores the target binding.
7. A Chrome restart removes the context. On the next normal browser command, create a clean replacement context, update the binding, return a structured `contextRecreated` warning/status, and apply configured `--state` or `--restore` inside the new context. Never fall back to the default context.
8. An explicit user `close` is the boundary destructor. Save configured restore state, dispose internal child contexts, dispose the primary context, and clear the isolated binding. It must not close Chrome or foreign targets.
9. Internal daemon restart, version restart, idle shutdown, signal shutdown, and connection rollback are detach paths unless they are also terminating a locally owned Chrome process. They must not dispose a context in an external shared Chrome.
10. `BrowserManager` owns one target-membership predicate based on `browserContextId`. Apply it to initial discovery, target-created and target-changed events, attached page/worker/iframe sessions, tab list/switch/close, popup handling, and target destruction.
11. Browser-level auto-attach may observe foreign contexts. Before any preparation, network control, navigation, registration, or close, foreign sessions must be immediately resumed and ignored.
12. Every target producer must declare its context before creation:
    - `tab new`, `window new`, click-new-tab, and state temporary targets use the primary context
    - recording and any feature requiring a child BrowserContext register that child before creating its target, then dispose it on feature stop or explicit boundary close
13. Cookie and storage commands continue using the active page session. State files remain backward-compatible `{cookies, origins}` documents. State save/load temporary targets use the primary context.
14. `--pin-tab` remains orthogonal. Isolation owns the context and target set; pinning owns the active target inside that set.
15. Do not add `context new/list/close` in this change. That is a separate product shape with multiple user-visible contexts per daemon, persistent refs, and a larger state contract.

### Why not `--context <name>`

The named `--session` already identifies the agent boundary. A separate cosmetic context name creates two identities that can drift. A true `context new/list/close` API is useful for multi-identity work inside one daemon, but it is not required to fix parallel agents and should be shaped separately.

### Material rejected

- `disposeOnDetach:true`: directly refuted by the daemon-restart probe.
- hard `context_gone` on Chrome restart: it blocks the existing restore recovery path and exposes an internal Chrome id as user identity.
- browser fingerprint: context enumeration plus target membership is enough for the current contract.
- optional new fields in the legacy binding shape: unsafe downgrade behavior.
- filtering only tab output: foreign auto-attach still interferes.
- user-managed multiple contexts in this issue: scope expansion.

## 7. Carried assumptions and implementation verification

Required tests:

1. Two isolated sessions, one Chrome, same origin, distinct cookies, localStorage, sessionStorage, IndexedDB, and cache.
2. A non-isolated session still sees the attached Chrome's default login state.
3. Isolated daemon restart preserves context id, target id, and storage.
4. Chrome restart creates a fresh context, never adopts default targets, reports recreation, and loads configured restore state.
5. Explicit close removes every owned target and context while preserving foreign targets and Chrome.
6. Internal daemon shutdown preserves the external context.
7. Foreign target creation does not change isolated `tab list`, active target, binding, network controls, or navigation.
8. Foreign auto-attached targets are resumed without installing controls or registering them.
9. Popups, workers, OOPIFs, `tab new`, `window new`, click-new-tab, recording, and state temporary targets stay inside owned contexts.
10. State save cannot collect localStorage from the default or another isolated context.
11. `--pin-tab` strict loss and recovery remain scoped inside the context.
12. Legacy state files load unchanged.
13. Legacy tab bindings load unchanged for non-isolated sessions.
14. A pre-isolation binary fails to parse an isolated binding instead of running without isolation.
15. Corrupt or unwritable isolated bindings fail before the daemon exposes a partially isolated session.

Mutation requirements:

- remove the discovery filter
- remove the event filter
- remove the state temp-target context id
- route internal shutdown through disposal
- omit child-context registration
- make the isolated binding backward-readable by an old binary
- fall back to the default context after Chrome restart

Each mutation must independently make a targeted test fail.
