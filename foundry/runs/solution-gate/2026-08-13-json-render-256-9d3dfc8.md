## Neutral contract

Property: public `repeat.statePath` must be interpreted consistently by validation, prompts, and all renderers; relative references are valid only within repeat scope and preserve JSON Pointer semantics.

Observable: a nested-repeat spec validates, compiles, and produces equivalent elements in every supported renderer; outside scope it never reads root state accidentally.

Must not change:

- Existing string paths.
- Per-item filtering.
- Indices and base paths.
- Bindings and actions.
- Non-nested repeats.

## Proposal A, verbatim

Exploration done: the interpretation of `repeat.statePath` today is root-absolute everywhere — eight renderer implementations (react, react-native, react-pdf, react-email, ink, vue, solid, svelte) each resolve it with `getByPath(rootState, statePath)` and build `basePath = statePath + "/" + index`; the validator resolves it against root sample state at `packages/core/src/spec-validator.ts:142`; prompts teach absolute-only at `packages/core/src/schema.ts:758-776`. There is no relative mechanism, so nested repeats over per-item arrays are currently inexpressible. / Exploración completa: hoy `repeat.statePath` se interpreta como puntero absoluto a la raíz en las ocho implementaciones de renderers, en el validador y en los prompts; no existe mecanismo relativo.

### Shape

**English.** State stays where it is: one root state store per renderer, and per-iteration scope (item, index, absolute basePath) stays in each renderer's existing RepeatScope context — nothing new is stored. The contract widens `repeat.statePath` from a plain string to a union: a string remains an absolute root JSON Pointer with today's exact semantics (including the lenient slashless parse in `parseJsonPointer`, `packages/core/src/types.ts:276`); a new object form reusing the repo's established `$item` convention (`{ "$item": "tasks" }`, empty string meaning the whole item, same shape as `$bindItem` in `packages/core/src/props.ts:182`) is a relative reference, valid only inside a repeat scope, resolved by JSON Pointer concatenation: enclosing scope's basePath + "/" + relative body, preserving RFC 6901 escaping. The inner scope's basePath keeps the existing formula (resolved absolute path + "/" + index), so `$item`, `$index`, `$bindItem`, per-item filtering, and array actions work unchanged inside nested scopes. Ownership of the interpretation decision moves to exactly one place: `@json-render/core` exports a single resolver that maps (statePath, scopeBasePath-or-null) to an absolute pointer or an explicit "unresolvable" result. Renderers own only plumbing — read their RepeatScope, pass its basePath to the resolver, render zero items and warn on unresolvable, never fall back to root. The structural validator owns static ancestry: it builds the parent chain from `children` arrays, simulates scope basePaths using item 0 of sample state through the same core resolver, keeps the existing `repeat_state_mismatch` check for absolute paths, and adds an error for the object form appearing outside any repeat ancestor. The prompt builder in `packages/core/src/schema.ts` owns teaching the two forms, and skills docs mirror it.

**Español.** El estado no se mueve: un único store raíz y el scope por iteración (item, índice, basePath absoluto) siguen viviendo en el contexto RepeatScope existente de cada renderer. El contrato amplía `statePath` a una unión: string = puntero absoluto a la raíz con la semántica actual intacta; forma objeto `{ "$item": "ruta" }` = referencia relativa válida solo dentro de un scope de repeat, resuelta por concatenación de JSON Pointers (basePath del scope + "/" + ruta), preservando el escapado de RFC 6901. La decisión de interpretación es propiedad exclusiva de un resolver único exportado por `@json-render/core`; los renderers solo suministran su basePath y renderizan cero ítems (con warning) cuando no resuelve, sin caer jamás en la raíz; el validador simula la cadena de ancestros con el mismo resolver y añade un error para la forma relativa fuera de scope; el prompt del sistema documenta ambas formas.

**Español.** (1) Hoy ningún renderer consulta el scope al resolver `statePath` — verificable con el comando `rg` indicado. (2) Tras el cambio, el fixture anidado produce exactamente 5 nodos en el mismo orden en todos los renderers — verificable con los comandos `pnpm vitest run` listados. (3) La forma relativa fuera de scope falla la validación y renderiza cero ítems, y las suites existentes pasan sin modificar sus archivos — cualquier fallo o edición de esos archivos la falsifica.

El compilador de TypeScript enumera gratis todos los consumidores del tipo ampliado.

### What it makes worse

**English.** `repeat.statePath` stops being a plain string in the public type. Every external consumer and internal tool that string-matches on it — the pattern in `packages/codegen/src/traverse.ts:61` (`collectStatePaths`), devtools inspectors, any user code doing `.startsWith("/")` — either breaks at compile time or silently skips the object form until taught the second shape. Additionally, static validation of relative paths becomes best-effort: when the outer sample array in `spec.state` is empty, the inner check must be skipped, creating a class of specs that validate cleanly yet render zero inner items at runtime.

**Español.** `statePath` deja de ser un string plano: toda herramienta que hace matching de strings sobre él (codegen, devtools, código de usuarios) rompe en compilación o ignora silenciosamente la forma objeto. Además, la validación estática de rutas relativas pasa a ser de mejor esfuerzo: con el array externo vacío en el estado de muestra, el chequeo interno se omite, y aparece una clase de specs que validan pero renderizan cero ítems.

### Rejected alternatives

**English.**
- Slashless strings as relative (`statePath: "tasks"`): killed by `parseJsonPointer` at `packages/core/src/types.ts:276`, which already resolves slashless strings as root-absolute today — reinterpreting them silently changes the meaning of existing string paths, which is explicitly off-limits.
- Draft Relative JSON Pointer syntax (`"0/tasks"`): killed by the same collision fact — leading-digit strings are valid root paths today (a state key `"0"` resolves) — and by the fact that no resolver for that draft exists in the codebase, while the `$item` relative-path convention already has one (`resolveBindItemPath`, `packages/core/src/props.ts:182`) and is already documented in prompts.
- Renderer-only change, leaving validator and prompts alone: killed by `packages/core/src/spec-validator.ts:142`, which resolves every statePath against root sample state and would emit a `repeat_state_mismatch` error for every relative reference — the nested spec would fail the "validates" half of the observable — and by `packages/core/src/schema.ts:760`, whose prompt teaches absolute-only so models would never emit the form.
- Per-renderer resolution logic with no shared core helper: killed by the count of independent implementations — eight `RepeatChildren` variants that must agree byte-for-byte, which have already drifted (ink's `packages/ink/src/renderer.tsx:326` handles the raw value differently from react's `renderer.tsx:489`).
- A sibling field `repeat.itemPath` instead of widening `statePath`: killed by the autofixer at `packages/core/src/spec-validator.ts:323`, which relocates whole misplaced `repeat` objects — a second path field creates a both-present precedence ambiguity and doubles the malformed-shape surface models already emit, whereas the `$item` object is an expression shape models produce correctly elsewhere in the same specs.

**Español.** Strings sin barra como relativos: lo mata `parseJsonPointer`, que hoy ya los resuelve como absolutos. Sintaxis draft de Relative JSON Pointer: la mata la misma colisión (strings con dígito inicial son rutas raíz válidas hoy) y la ausencia de resolver, frente a la convención `$item` ya implementada. Cambio solo en renderers: lo mata el validador, que marcaría error toda ruta relativa, y el prompt que solo enseña absolutas. Resolución por renderer sin helper en core: la matan las ocho implementaciones independientes que ya divergieron. Campo hermano `itemPath`: lo matan la ambigüedad de precedencia y el autofixer que recoloca objetos `repeat` completos.

## Proposal B, verbatim

### Shape
Where state lives: State remains entirely within a single JSON tree at the root. The active repeat scope continues to store an absolute JSON Pointer (the base path) to its specific array item.

Who owns each decision: A central path-resolution utility owns the logic for determining if a state path is absolute or relative, and for merging relative paths with a base path. Framework renderers, the core validator, and prompt generators own the responsibility of invoking this utility with the current scope's base path before reading state.

What the contract becomes: The repeat state path remains a single string. A leading slash explicitly denotes an absolute JSON Pointer from the root state. A missing leading slash denotes a relative pointer; it must be concatenated with the active repeat scope's base path using a slash delimiter. If a relative pointer is evaluated outside of any repeat scope, it resolves to an invalid or empty value and never falls back to reading the root state.

### Predictions
1. The raw usage of repeat state paths will disappear from state lookups in renderers.
Command: `rg "getByPath\([^,]+,\s*[^.]+\.repeat\.statePath\)" packages/`
Measurement: Returns exit code 1 (zero matches).

2. Relative paths used outside a repeat scope will fail validation instead of unexpectedly resolving against the root.
Command: `npx vitest run packages/core/src/spec-validator.test.ts`
Measurement: Passes successfully after adding a test asserting that a root-level element with `{ repeat: { statePath: "tasks" } }` throws a `repeat_state_mismatch` error.

### Cost
- All eight framework renderers (Vue, React, Svelte, Solid, Ink, React Native, React PDF, React Email) must be updated.
- The core specification validator must be updated to maintain a stack of active base paths during tree traversal to correctly validate nested relative repeats.
- The central path resolution must be isolated to repeats or explicitly opted-in to ensure we do not break existing lenient parsing for bindings and actions.

### What it makes worse
Renderer component logic becomes more tightly coupled to its context. A component can no longer evaluate its `repeat` directive in isolation using only the root state; it must first inject and read the parent's repeat scope to determine its own iteration path, increasing the rendering sequence complexity.

### Rejected alternatives
- Adding a dedicated `relativePath` property to the repeat schema. Fact that kills it: Violates the constraint "Must not change: Existing string paths" by fragmenting the path API.
- Modifying the core JSON Pointer parser to globally reject paths without leading slashes. Fact that kills it: Violates the constraint "Must not change: bindings and actions", which currently rely on lenient path parsing.
- Dynamically checking the current item for the property and falling back to the root state if missing. Fact that kills it: Name collisions (e.g. both root and item having a `tasks` array) would cause unpredictable data binding, violating the constraint to "preserve JSON Pointer semantics".

## Forward chains

### Proposal A: explicit `$item` object

1. Widen `repeat.statePath` to `string | { $item: string }`.
   - Mechanism: TypeScript exposes every consumer that assumes a string.
   - Mark: inferred from `packages/core/src/types.ts:71` and the current main build failure seen when PR #256 is applied.
2. Route both forms through one core resolver.
   - Mechanism: renderers no longer invent their own fallback or path joining rules.
   - Mark: inferred from repeated raw lookup and base-path construction across renderer packages.
3. Resolve the object form only when an enclosing repeat supplies an absolute item base path.
   - Mechanism: the resolver returns `undefined` without scope, so runtime renders zero items instead of reading root state.
   - Mark: inferred.
4. Feed the resolved absolute path into the existing item base-path formula.
   - Mechanism: nested scopes continue exposing absolute paths to `$bindItem`, actions, indices, and child repeats.
   - Mark: inferred.
5. Harmful branch: external consumers that assume `statePath` is a string may compile-fail or ignore the object form.
   - Mechanism: the public union changes narrowing requirements.
   - Mark: inferred; `packages/codegen/src/traverse.ts` was inspected and does not currently collect top-level `repeat.statePath`.
6. Harmful branch: validation cannot prove inner array shape when sample outer arrays are empty.
   - Mechanism: there is no representative item path to resolve statically.
   - Mark: guessed; implementation must keep this limitation explicit and must still reject relative use outside structural scope.

### Proposal B: slashless strings become relative

1. Keep `repeat.statePath` as a string and classify it by leading slash.
   - Mechanism: `/tasks` remains absolute while `tasks` becomes relative.
   - Mark: proposal.
2. Existing slashless repeat paths change meaning.
   - Mechanism: `getByPath` currently treats `"user/name"` as a root path, and the type permits the same string in repeats.
   - Mark: observed by source and test execution.
3. Harmful branch: a root repeat using `statePath: "tasks"` becomes invalid outside a repeat scope.
   - Mechanism: the new classifier reinterprets a previously valid root lookup as relative.
   - Mark: observed consequence.
4. Harmful branch: validation and runtime disagree with historical lenient JSON Pointer behavior unless repeat paths alone get a new grammar.
   - Mechanism: the proposal creates a repeat-specific string interpretation unlike `getByPath`, bindings, and actions.
   - Mark: inferred.
5. Beneficial branch: public TypeScript shape stays a string.
   - Mechanism: no union propagates to external consumers.
   - Mark: inferred.

## Synthesis

Kind: one proposal whole.

Take Proposal A's explicit `{ "$item": string }` shape, with these required refinements:

1. A shared core resolver owns path interpretation and JSON Pointer joining.
2. Strings keep exact current semantics, including no-leading-slash root paths.
3. Relative bodies accept both `"subitems"` and `"/subitems"` without producing a double slash.
4. Relative use outside repeat scope resolves to no path, warns at runtime, and is a validation error when structurally outside repeat ancestry. It never falls back to root state.
5. Validator, prompt builder, docs, skills, Svelte, framework renderers, and static render functions are part of the same contract change.
6. Existing base paths remain absolute, so bindings, actions, filters, and indices continue to consume the same scope contract.

Proposal B's genuinely better property is the smaller public type surface. It is not taken because the only available string distinction collides with existing, tested path semantics. Its central-resolver ownership is already present in Proposal A.

## Carried assumptions and implementation verification targets

- The shared resolver is usable from every renderer package without creating dependency cycles.
- Leading slash in `$item` bodies is normalization, not a request to escape the parent scope.
- Empty `$item` resolves to the enclosing item path.
- Outside-scope relative repeat renders zero items in every runtime path.
- Nested repeat base paths remain absolute and preserve RFC 6901 escaped tokens.
- Existing repeat-filter, binding, action, index, and non-nested repeat tests remain green without weakening assertions.
- Svelte type-check and nested repeat behavior are covered.
- Static image, React Email, and React PDF render functions use the same resolver as component renderers.
